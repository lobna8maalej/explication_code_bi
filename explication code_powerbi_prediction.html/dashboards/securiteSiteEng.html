1. General Overview of Security

In this part of the project, a complete authentication and route security system has been implemented to protect access to sensitive application features. The system mainly relies on several complementary technologies: Node.js for backend execution, Express for creating HTTP routes, Sequelize as an ORM for communicating with MySQL, bcryptjs for protecting passwords, and JSON Web Token, called JWT, for managing user authentication. The general principle is to allow a user to create an account with a name, email address and password, and then log in using this information. During registration, the original password is never stored directly in the database. It is transformed into a hashed value using bcrypt. During login, the password provided by the user is compared with the hash stored in MySQL. If the information is correct, the server generates a JWT token containing certain information used to identify the user. The frontend then receives this token and must send it when accessing protected routes. The autorize middleware retrieves the token from the HTTP Authorization header, verifies its validity using jwt.verify() and the secret key JWT_SECRET. When the token is valid, the decoded information is placed in req.user and the next() function allows the request to continue. If no token is provided or if the token is invalid or expired, the server blocks access and returns an HTTP 401 Unauthorized response. The architecture therefore clearly separates several security levels: user management in MySQL, password protection with bcrypt, authentication with JWT, and route protection with Express middleware.

2. Connecting to MySQL with Sequelize

The first level of the system corresponds to the connection between the Node.js server and the MySQL database. To establish this connection, the project uses Sequelize. Sequelize is an ORM that allows a relational database to be manipulated through JavaScript models. This means that the developer can use methods such as findOne() or create() instead of writing all SQL queries directly. In the config/db.js file, the Sequelize library is imported with const { Sequelize, DataTypes } = require("sequelize"). The sequelize object is then created with the database name POWERBI_PREDICTION, the MySQL user root, an empty password in this development environment, the host localhost and the mysql dialect. The localhost parameter indicates that MySQL is running on the same machine as the Node.js server, while dialect: "mysql" tells Sequelize that the database management system being used is MySQL. Finally, the connection is exported using module.exports so that it can be used by the application's models and controllers. This organization makes it possible to centralize the database configuration and reuse the same connection throughout the different parts of the backend. 

const { Sequelize, DataTypes } = require("sequelize");

const sequelize = new Sequelize(
    "POWERBI_PREDICTION",
    "root",
    "",
    {
        host: "localhost",
        dialect: "mysql"
    }
);

module.exports = {
    sequelize,
};

3. Creating the User Model

The User model represents the structure of users registered in the database. The file begins by importing DataTypes from Sequelize as well as the sequelize connection defined in config/db.js. The function sequelize.define("User", ...) is then used to create a model called User. This model contains four main pieces of information: the identifier, name, email and password. The id field is an integer type using DataTypes.INTEGER, it is automatically incremented with autoIncrement: true and constitutes the primary key with primaryKey: true. The name field is a string and allowNull: false indicates that the name is required. The email field is also a string, it is required and has the unique: true property. This prevents multiple accounts from using the same email address. Finally, the password field is required and is used to store the password in its hashed form. It is very important to specify that the value stored in this column must not be the original password. The controller uses bcrypt before saving the password in order to transform it into a hash. 

const { DataTypes } = require("sequelize");
const { sequelize } = require("../config/db");

const User = sequelize.define("User", {

    id: {
        type: DataTypes.INTEGER,
        autoIncrement: true,
        primaryKey: true,
    },

    name: {
        type: DataTypes.STRING,
        allowNull: false,
    },

    email: {
        type: DataTypes.STRING,
        allowNull: false,
        unique: true,
    },

    password: {
        type: DataTypes.STRING,
        allowNull: false,
    },

});

module.exports = User;

4. Register Function: User Registration

The register function is responsible for registering a new user. It is declared with async because it performs several asynchronous operations, including database searches, password hashing and user creation. The name, email and password information is retrieved from req.body, which means that it is sent by the frontend in the body of the HTTP request. Before creating the account, the server uses User.findOne() with where: { email } to check whether a user already has this email address. If a user exists, registration is immediately stopped and the server returns an HTTP 400 response with the message Email already in use. This check is important because it prevents multiple accounts from being created with the same email address. If no account exists, the server then uses bcrypt.hash(password, 10). This operation transforms the original password into a hashed value. The number 10 represents the computational cost used by bcrypt to generate the hash. The original password is therefore not directly stored in MySQL. After this step, User.create() creates the user with the name, email and hashed password. Once the user has been created, the server generates a JWT token using jwt.sign(). The token payload contains the user's identifier and email. The token is signed with the secret key stored in process.env.JWT_SECRET and its validity period is set to seven days using expiresIn: "7d". Finally, the server returns an HTTP 201 response containing the user and the token. The frontend can then use this token for future requests requiring authentication. 

exports.register = async (req, res) => {
    try {

        const { name, email, password } = req.body;

        const exist = await User.findOne({
            where: { email }
        });

        if (exist) {
            return res.status(400).json(
                "Email déjà utilisé"
            );
        }

        const hashedPassword =
            await bcrypt.hash(password, 10);

        const user = await User.create({
            name,
            email,
            password: hashedPassword,
        });

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.status(201).json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

5. Login Function: User Login

The login function allows a registered user to log in to the application. The server retrieves the email and password from req.body, then uses User.findOne() to search for the user corresponding to this email address in MySQL. If no user is found, the server returns an HTTP 400 response with the message User not found. If the user exists, the server does not directly compare two plain-text passwords. Instead, it uses bcrypt.compare(password, user.password) to compare the entered password with the hash stored in the database. If the comparison returns false, the server rejects the login with the message Incorrect password. If the password is correct, the server generates a new JWT token using jwt.sign(). As during registration, the token contains the user's identifier and email, it is signed with JWT_SECRET and has a validity period of seven days. The server then returns a JSON object containing the user and the token. The frontend can store this token and send it when accessing protected features. This step therefore represents the application's authentication mechanism: the user proves their identity using their email and password, then receives a token allowing the server to recognize this authentication during subsequent requests. 

exports.login = async (req, res) => {
    try {

        const { email, password } = req.body;

        const user = await User.findOne({
            where: { email },
        });

        if (!user) {
            return res.status(400).json(
                "Utilisateur introuvable"
            );
        }

        const validPassword =
            await bcrypt.compare(
                password,
                user.password
            );

        if (!validPassword) {
            return res.status(400).json(
                "Mot de passe incorrect"
            );
        }

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

6. Authentication with JSON Web Token

JSON Web Token, generally called JWT, is used in this project to manage authentication between the frontend and backend. After a successful registration or login, the server generates a token using jwt.sign(). This token contains a payload with information used to identify the user, including their id and email. The token is signed with process.env.JWT_SECRET. This secret key is important because it allows the server to verify that the token presented by the client corresponds to a token signed by the server. The key must be stored in an environment variable and must not be directly published in the source code. The token also has a validity period of seven days through expiresIn: "7d". This means that an expired token should no longer allow access to protected routes. JWT therefore avoids sending the password with every request. Once logged in, the frontend uses the token as proof of authentication and sends it to the backend when it wants to access a protected route.

Important principle:

JWT does not replace the password and should not be considered the password. It represents temporary proof of authentication created by the server.

7. autorize Middleware: Route Protection

The autorize.js file contains an Express middleware whose role is to control access to protected routes. The middleware first imports the jsonwebtoken library. The autorize function receives three parameters: req, which represents the HTTP request, res, which is used to send the response to the client, and next, which allows execution to continue to the next function when the user is authorized. The middleware then retrieves the token from req.headers.authorization. The frontend must send the header in the form Authorization: Bearer TOKEN. The split(" ") method separates the word Bearer from the token and index [1] retrieves only the token. The ?. operator prevents an error if the header does not exist. The middleware then checks whether the token is present. If no token is found, access is immediately denied with HTTP status 401 and the message Missing token. If the token exists, the server uses jwt.verify() with the token and process.env.JWT_SECRET. This operation verifies that the token is valid and has not expired. If verification succeeds, the decoded information is placed in req.user. This step is very useful because subsequent functions can now identify the authenticated user. Finally, next() allows the request to continue to the protected route. If verification fails, for example because the token is invalid or expired, execution enters the catch block and the server returns an HTTP 401 response with the message Invalid token. Thus, the middleware acts as a real security barrier in front of sensitive routes. 

const jwt = require("jsonwebtoken");

const autorize = (req, res, next) => {

    const token =
        req.headers.authorization?.split(" ")[1];

    if (!token) {

        return res.status(401).json({
            message: "Token manquant",
        });

    }

    try {

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        req.user = decoded;

        next();

    } catch (error) {

        return res.status(401).json({
            message: "Token invalide",
        });

    }
};

module.exports = autorize;

8. Registration and Login Routes

The user routes file connects controller functions to the HTTP endpoints of the application. Express provides the Router() function for creating a set of independent routes. The file then imports the register and login functions from the user controller. The first route is router.post("/register", register). It indicates that when an HTTP POST request is sent to /register, Express executes the register function. This function receives the form data, verifies the email, hashes the password, creates the user and generates the JWT. The second route is router.post("/login", login). When a POST request is sent to /login, Express executes the login function. This function verifies the user, compares the password with bcrypt and generates a new JWT token if the information is correct. Finally, module.exports = router exports the router so that it can be used in the main server file. This separation between routes and controllers allows the backend to be properly organized: routes define URLs and HTTP methods, while controllers contain the business logic. 

const express = require("express");

const router = express.Router();

const { sequelize } = require("../config/db");

const {
    register,
    login,
} = require("../Controllers/userController");

router.post("/register", register);

router.post("/login", login);

module.exports = router;

9. JWT-Protected Admin Route

A special route also demonstrates concretely how the security middleware is used. The Express router defines the GET /admin route and places the autorize middleware between the URL and the controller. The order is very important: when a request arrives at this route, Express first executes autorize. The middleware retrieves the JWT token from the Authorization header, verifies its validity using jwt.verify(), places the user's information in req.user, and then calls next(). Only after this verification is the route function executed. If the token is missing, the route controller is never executed and the server returns a 401 error. If the token is invalid or expired, the same principle applies. When the token is valid, the route can return the message Welcome Admin together with the user contained in req.user. This route therefore shows how middleware becomes a barrier between the client and a protected feature. However, authentication must be distinguished from authorization: the middleware presented here verifies that the token is valid and identifies the user, but the provided code does not yet verify that the user actually has an administrator role. To implement true role-based authorization, a role such as admin or user should also be stored in the user model and this role should be checked before granting access to a route strictly reserved for administrators. 

const express = require("express");
const router = express.Router();

const autorize =
    require("../middleware/autorize");

/* =========================
   ADMIN ROUTE
========================= */

router.get(
    "/admin",
    autorize,
    (req, res) => {

        res.json({
            message: "Bienvenue Admin",
            user: req.user,
        });

    }
);

module.exports = router;
⚠️ Important point:

In the current code, the middleware verifies that the user possesses a valid JWT, but it does not yet verify that the user actually has the admin role. The name of the /admin route indicates a route intended for administration, but the current security mainly corresponds to authentication. An additional role check would be necessary to implement true administrator authorization.

10. Complete System Operation

The overall security process begins when the user uses the frontend to create an account. The frontend sends a POST request to the /register route with the name, email and password. Express receives this request and calls the register controller. The controller checks in MySQL, through Sequelize, whether the email already exists. If the address is available, bcrypt transforms the password into a hash and Sequelize creates the new user in the database. The server then generates a JWT signed with JWT_SECRET and valid for seven days. During login, the frontend uses the /login route. The controller searches for the user by email and then uses bcrypt.compare() to verify the password. If the information is correct, a JWT is generated and sent to the frontend. To access a protected route such as /admin, the frontend must send the token in the Authorization header using the format Bearer TOKEN. Express then executes the autorize middleware. It retrieves the token, uses jwt.verify() to check its validity and places the user's information in req.user. If verification succeeds, next() allows the request to continue. If the token is missing, invalid or expired, access is denied with an HTTP 401 error. This architecture therefore creates a complete security chain from the frontend to Express, then through the JWT middleware, controller, Sequelize and finally MySQL.

11. Different Security Layers

Application security relies on several complementary mechanisms rather than a single technology. First, Sequelize structures user data and communicates with MySQL. Second, the User model imposes certain constraints such as requiring the name, email and password, as well as ensuring email address uniqueness. Third, bcrypt protects passwords through hashing before they are stored. Fourth, bcrypt.compare() allows passwords to be verified without storing the original password. Fifth, JWT provides a mechanism that allows the server to recognize an authenticated user. Sixth, JWT_SECRET is used to sign and verify tokens. Seventh, token expiration after seven days limits its validity period. Eighth, the autorize middleware acts as a barrier in front of protected routes. Finally, HTTP status codes such as 400, 401 and 500 make it possible to handle different error situations. All these elements work together to create a structured and more secure authentication architecture than an application that stores passwords in plain text or leaves all routes accessible without control.

12. Security Error Handling

The system handles several error situations. When a user attempts to create an account with an email address that is already in use, the server returns status 400 with the message Email already in use. When a user attempts to log in with an address that does not exist, the server returns User not found. When the address exists but the password is incorrect, bcrypt.compare() returns false and the server returns Incorrect password. For protected routes, if no JWT is sent, the middleware returns 401 with Missing token. If the JWT is invalid or expired, jwt.verify() triggers an error that is caught by the catch block, and the server returns 401 with Invalid token. Finally, unexpected errors originating from the server or database can be caught by the try/catch blocks in the controllers and return status 500. This handling allows the frontend to understand the result of the request and display an appropriate message to the user.

This architecture therefore clearly separates registration, login, password hashing, JWT generation and route protection. It forms the foundation of the backend security of my application.

14. Conclusion

The developed system provides complete authentication between the frontend, backend and MySQL database. Sequelize handles communication with MySQL and allows the User model to be defined. The Express routes /register and /login respectively allow an account to be created and authentication to be performed. Using bcrypt ensures that passwords are not stored directly in their original form. JWT then represents the user's authentication state for a limited period of time. The autorize middleware verifies the token before allowing a request to access a protected route. Through jwt.verify(), the server can verify the token and retrieve the user's information in req.user. Protected routes can therefore control access to sensitive features. The current architecture therefore provides a solid backend security foundation using Node.js, Express, Sequelize, MySQL, bcrypt and JWT. For even more complete security in a real production application, this foundation can later be strengthened with role and permission management, strict data validation, protection against brute-force attacks, HTTPS, secure token storage and better management of sensitive information.
