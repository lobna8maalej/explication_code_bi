💊 Dashboard Parapharma — Explication du code

Documentation technique du fonctionnement de Redux Toolkit, React, Axios, Recharts et Power BI pour la récupération, la prédiction et la visualisation des données de parapharmacie.

# 74 — Gestion des données Parapharma avec Redux Toolkit et React

Dans cette partie du projet, un système de récupération et de visualisation des données de parapharmacie a été développé en utilisant plusieurs technologies frontend complémentaires, notamment React, Redux Toolkit, Axios, Recharts et Power BI. L'objectif principal de cette fonctionnalité est de permettre à l'utilisateur d'accéder à un dashboard consacré aux données de parapharmacie. Le dashboard combine un rapport Power BI intégré, l'affichage des données réelles, les valeurs de prédiction et un graphique permettant de comparer visuellement les valeurs réelles et prédites. Contrairement au dashboard Immobilier présenté précédemment, cette fonctionnalité ne contient pas de bouton permettant à l'utilisateur d'insérer manuellement les données. Les données sont récupérées automatiquement depuis le backend lorsque le composant React est chargé. Redux Toolkit est utilisé pour centraliser l'état des données Parapharma, tandis que React est responsable de leur affichage dans l'interface. Axios assure la communication HTTP avec le backend Node.js/Express. La bibliothèque Recharts permet ensuite de transformer les données reçues en graphique. Le rapport Power BI est quant à lui intégré directement dans la page grâce à une iframe. L'architecture permet donc de réunir dans une même interface la récupération des données, la prédiction, la visualisation graphique et la Business Intelligence.

# 75 — Importation de Redux Toolkit et Axios

Le fichier Redux commence par l'importation de createSlice et createAsyncThunk depuis @reduxjs/toolkit. Ces deux fonctionnalités jouent des rôles différents dans la gestion de l'état. La fonction createSlice() permet de créer une partie du store Redux dédiée aux données de parapharmacie. Elle permet notamment de définir le nom du slice, son état initial et les traitements associés aux différentes étapes de l'opération asynchrone. La fonction createAsyncThunk() permet quant à elle de créer une action asynchrone destinée à effectuer une opération telle qu'une requête HTTP vers un serveur. Le fichier importe également axios grâce à l'instruction import axios from "axios". Axios est utilisé ici pour communiquer avec l'API backend. L'association de Redux Toolkit et Axios permet donc de séparer la gestion de l'état de la logique de communication avec le serveur.

# 76 — Création de l'action asynchrone fetchParapharma

L'action principale du fichier Redux est fetchParapharma. Elle est créée grâce à createAsyncThunk(). Le premier paramètre "parapharma/fetchParapharma" correspond au type de l'action Redux. Il permet d'identifier cette opération dans l'application. Le deuxième paramètre est une fonction asynchrone qui reçoit deux paramètres : _ et thunkAPI. Le premier paramètre est représenté par _ car aucune donnée particulière n'est nécessaire pour déclencher cette action. Le thunk est donc lancé sans argument. Le deuxième paramètre, thunkAPI, fournit plusieurs fonctionnalités de Redux Toolkit, notamment rejectWithValue(), utilisée ici pour transmettre proprement une erreur au reducer Redux. La fonction contient ensuite un bloc try/catch. Le bloc try contient la communication avec le backend tandis que le bloc catch prend en charge les éventuelles erreurs.

# 77 — Requête GET vers le backend Parapharma

À l'intérieur du bloc try, Axios effectue une requête HTTP GET grâce à l'instruction axios.get("http://localhost:3000/parapharma"). Cette requête permet au frontend de demander les données de parapharmacie au backend. L'adresse http://localhost:3000/parapharma représente ici l'endpoint de l'API utilisé pour récupérer les informations. La méthode GET signifie que le frontend demande des données au serveur sans envoyer un nouveau jeu de données à enregistrer. Lorsque le backend répond, la réponse complète est stockée dans la constante response. Le code utilise ensuite return response.data. Cette instruction retourne les données contenues dans la réponse HTTP. Redux Toolkit utilise alors cette valeur comme payload de l'action fulfilled si la requête réussit. Le frontend peut ainsi récupérer les données retournées par l'API et les enregistrer dans le store Redux.

# 78 — Gestion des erreurs avec rejectWithValue

Le bloc catch permet de gérer les erreurs pouvant apparaître pendant la communication avec le backend. Le code utilise thunkAPI.rejectWithValue() afin de transmettre une information d'erreur personnalisée au reducer Redux. L'expression error.response?.data?.error || error.message essaie d'abord de récupérer un message d'erreur envoyé directement par le backend. L'opérateur ?., appelé optional chaining, permet d'accéder à une propriété sans provoquer une nouvelle erreur si l'une des propriétés précédentes n'existe pas. Si le backend ne fournit pas de message d'erreur dans error.response.data.error, le code utilise alors error.message, qui correspond au message fourni par Axios ou JavaScript. Cette valeur est ensuite transmise à Redux grâce à rejectWithValue(). Le reducer rejected pourra alors récupérer cette information avec action.payload et l'enregistrer dans le state.

# 79 — Création du slice Parapharma

Le code crée ensuite le slice Redux grâce à createSlice(). Le slice est identifié par name: "parapharma". Cette propriété indique que cette partie du store Redux est consacrée à la fonctionnalité Parapharma. Le slice contient également une propriété initialState qui définit les valeurs initiales du state. Cet état initial contient cinq informations principales : loading, error, message, rowsInserted et items. La propriété loading indique si la récupération des données est actuellement en cours. Elle est initialisée à false car aucune requête n'est exécutée au démarrage du store. La propriété error est initialisée à null afin de pouvoir stocker une éventuelle erreur. message contient initialement une chaîne vide. rowsInserted est initialisé à zéro et permettra de recevoir le nombre de lignes retourné par le backend. Enfin, items est initialisé avec un tableau vide destiné à recevoir les données Parapharma retournées par l'API.

# 80 — Gestion de l'état pending

Lorsque l'action fetchParapharma() est déclenchée, Redux Toolkit démarre automatiquement l'état pending. Le code utilise .addCase(fetchParapharma.pending, ...) afin de définir les modifications à effectuer pendant cette phase. La première instruction est state.loading = true. Cette valeur indique à l'application React qu'une requête de récupération des données est actuellement en cours. Le code définit également state.error = null. Cette instruction permet d'effacer une éventuelle ancienne erreur avant de commencer une nouvelle récupération. Dans le composant React, la propriété loading sera ensuite utilisée pour afficher le message « Loading prediction... ». L'état pending constitue donc la première étape du cycle asynchrone : Redux signale au composant que les données ne sont pas encore disponibles et que le frontend doit patienter jusqu'à la réponse du backend.

# 81 — Gestion de l'état fulfilled

Lorsque la requête GET vers le backend réussit, Redux Toolkit déclenche automatiquement l'état fulfilled. Le reducer associé reçoit alors les informations retournées par le thunk dans action.payload. La première instruction est state.loading = false, ce qui indique que la récupération des données est terminée. Le code récupère ensuite le message du backend avec state.message = action.payload.message. Le nombre de lignes est enregistré avec state.rowsInserted = action.payload.rowsInserted. Enfin, les données principales sont enregistrées avec state.items = action.payload.data. Cette dernière propriété est particulièrement importante car elle contient le tableau de données utilisé ensuite par le composant React. Les informations retournées par le backend suivent donc un parcours clair : elles sont reçues par Axios, retournées par le thunk, deviennent le payload de fulfilled, puis sont enregistrées dans le store Redux. React pourra ensuite récupérer ces valeurs grâce à useSelector().

# 82 — Gestion de l'état rejected

Lorsque la requête Axios échoue, Redux Toolkit déclenche l'état rejected. Cette situation peut se produire lorsque le backend est arrêté, lorsque l'endpoint /parapharma est incorrect, lorsqu'une erreur serveur se produit ou lorsqu'un problème réseau empêche la communication. Le reducer utilise alors .addCase(fetchParapharma.rejected, ...). La première instruction remet state.loading à false, car la requête est terminée même si elle a échoué. Le code stocke ensuite l'erreur grâce à state.error = action.payload. La valeur action.payload correspond à l'information transmise précédemment par rejectWithValue(). Le composant React récupère ensuite cette valeur et peut afficher le message d'erreur grâce à la condition {error && ...}. Le cycle Redux Toolkit est donc entièrement géré avec les trois états pending, fulfilled et rejected.

# 83 — Exportation du reducer Parapharma

À la fin du fichier Redux, l'instruction export default parapharmaSlice.reducer permet d'exporter le reducer créé par createSlice(). Ce reducer doit ensuite être enregistré dans le store Redux principal de l'application. Une fois enregistré, le state parapharma devient accessible dans les composants React. Le composant ParapharmaDashboard peut alors utiliser useSelector() pour récupérer les informations du state et useDispatch() pour déclencher l'action fetchParapharma(). Cette organisation permet de centraliser toute la logique de récupération et de gestion des données Parapharma dans un fichier Redux dédié.

# 86 — Création du composant ParapharmaDashboard

La fonction ParapharmaDashboard() représente la page principale du dashboard Parapharma. Elle regroupe plusieurs fonctionnalités dans une même interface. # 87 — Utilisation de useDispatch

Le code utilise l'instruction const dispatch = useDispatch() afin d'obtenir la fonction permettant d'envoyer des actions vers Redux. Dans ce composant, dispatch est utilisé dans le useEffect() avec l'instruction dispatch(fetchParapharma()). Cela signifie que le composant demande à Redux d'exécuter l'action asynchrone fetchParapharma. Il passe par Redux, ce qui permet de centraliser la logique de récupération des données. Cette approche rend le code plus organisé et facilite la maintenance de l'application.

# 88 — Récupération du state avec useSelector

Le composant récupère ensuite les informations du slice Parapharma grâce à useSelector(). L'instruction useSelector((state) => state.parapharma) permet d'accéder à l'ensemble du state associé à la fonctionnalité. Le code extrait ensuite cinq propriétés : loading, error, message, rowsInserted et items. loading indique si la récupération des données est en cours. error contient une éventuelle erreur. message contient le message retourné par le backend. rowsInserted représente le nombre de lignes retournées ou traitées. Enfin, items contient le tableau principal des données Parapharma. Grâce à useSelector(), React reste synchronisé avec Redux. Lorsque Redux modifie une de ces valeurs, le composant est automatiquement réexécuté et l'interface est mise à jour.

# 89 — Récupération automatique des données avec useEffect

Le code utilise ensuite le hook useEffect() pour déclencher automatiquement la récupération des données lorsque le composant est chargé. L'instruction useEffect(() => { dispatch(fetchParapharma()); }, [dispatch]) indique que l'action fetchParapharma() doit être exécutée après le rendu du composant. Grâce à cette logique, l'utilisateur n'a pas besoin de cliquer sur un bouton pour demander les données. Dès que la page Parapharma est affichée, React déclenche le dispatch vers Redux. Redux lance alors le thunk, qui utilise Axios pour envoyer la requête GET vers /parapharma. Le tableau de dépendances contient dispatch. Cette organisation permet à React de gérer correctement l'effet et d'éviter une exécution inutile lors des rendus suivants. Le chargement des données est donc automatisé dès l'ouverture du dashboard.

# 90 — Transformation des données pour Recharts

Le composant crée ensuite une constante appelée chartData. Cette constante transforme les données présentes dans items afin de les adapter au format attendu par Recharts. Le code utilise items.map((item, index) => (...)) pour parcourir chaque élément du tableau. Pour chaque élément, un nouvel objet est créé avec trois propriétés. La propriété name reçoit une valeur telle que Data 1, Data 2, Data 3, etc. Cette valeur sera utilisée comme catégorie sur l'axe horizontal du graphique. La propriété Reel reçoit la valeur item.real, correspondant à la valeur réelle fournie par les données. La propriété Prediction reçoit item.prediction, correspondant à la valeur prédite. Cette transformation est importante car elle prépare les données reçues du backend dans une structure directement exploitable par le composant BarChart.

Le composant utilise la propriété loading récupérée depuis Redux pour déterminer si les données sont encore en cours de récupération. # 93 — Affichage des erreurs

Le composant prévoit également un mécanisme d'affichage des erreurs grâce à la condition {error && ...}. Si la propriété error contient une valeur, un paragraphe possédant la classe CSS error est affiché. Le contenu du paragraphe correspond à la valeur de error. Cette valeur provient du reducer rejected du slice Redux. Lorsqu'une erreur se produit dans Axios, le bloc catch utilise rejectWithValue() pour transmettre le message au reducer. Celui-ci stocke ensuite la valeur dans state.error. React récupère cette information grâce à useSelector() et l'affiche dans l'interface. L'utilisateur est donc informé directement lorsqu'un problème empêche la récupération des données Parapharma.

# 94 — Affichage du message et du nombre de lignes

Lorsque le chargement est terminé et qu'aucune erreur n'est présente, le composant affiche les informations retournées par le backend grâce à la condition {!loading && !error && (...)}. Dans cette partie, une carte d'information possédant la classe info-card est affichée. Le titre <h2>{message}</h2> présente le message reçu depuis le backend. Le paragraphe Rows inserted: {rowsInserted} affiche ensuite le nombre de lignes retourné par l'API. Ces informations ne sont donc pas écrites en dur dans le composant. Elles proviennent du backend, sont transmises par Axios, stockées dans Redux puis récupérées par React. Cette chaîne permet d'afficher dynamiquement le résultat du traitement des données Parapharma.

# 101 — Communication complète entre React, Redux, Axios et Backend

Le fonctionnement complet commence lorsque l'utilisateur ouvre le Parapharma Dashboard. React charge le composant ParapharmaDashboard. Après son rendu, le hook useEffect() déclenche automatiquement dispatch(fetchParapharma()). Redux Toolkit déclenche alors l'état pending et met loading à true. Le thunk fetchParapharma utilise ensuite Axios pour envoyer une requête HTTP GET vers http://localhost:3000/parapharma. Le backend reçoit la requête, récupère ou traite les données Parapharma et retourne une réponse JSON. Si la communication réussit, le thunk retourne response.data. Redux déclenche alors l'état fulfilled et enregistre le message, le nombre de lignes et les données dans le store. Si la requête échoue, le bloc catch utilise rejectWithValue() et Redux déclenche rejected. Le composant récupère ensuite les informations avec useSelector(). Les données items sont transformées en chartData, puis utilisées par Recharts pour construire le graphique « Réel vs Prediction ». React met automatiquement à jour l'interface lorsque le state Redux change. Le rapport Power BI reste parallèlement intégré dans la page grâce à l'iframe.

Cette architecture permet donc d'associer récupération de données, prédiction, visualisation graphique et Business Intelligence dans une même application frontend.

# 105 — Cycle complet de récupération et de prédiction

Le cycle commence lorsque l'utilisateur accède à la page Parapharma Dashboard. React affiche le composant et exécute le hook useEffect(). Celui-ci déclenche dispatch(fetchParapharma()). Redux Toolkit démarre alors l'état pending et met loading à true. Le thunk utilise Axios pour envoyer une requête GET vers /parapharma. Le backend traite la demande et retourne les informations nécessaires. Si la réponse est correcte, Redux déclenche fulfilled. Le message est enregistré dans message, le nombre de lignes dans rowsInserted et les données dans items. React récupère ces informations grâce à useSelector(). Chaque élément contient notamment une valeur réelle et une valeur de prédiction. Le composant transforme ensuite ces informations en chartData. Recharts utilise ces données pour construire un graphique comparant Réel et Prediction. Si une erreur apparaît pendant la requête, Redux déclenche au contraire rejected et l'erreur est affichée dans l'interface. Le système permet donc de suivre automatiquement le parcours des données depuis le backend jusqu'à leur représentation finale.

# 106 — Différence entre les données Réel et Prediction

Une partie essentielle de ce dashboard consiste à comparer deux types de valeurs : les valeurs réelles et les valeurs de prédiction. Dans les données reçues depuis le backend, la propriété real représente la valeur observée ou réelle. La propriété prediction représente quant à elle la valeur produite par le modèle de prédiction. Le composant transforme ces deux propriétés dans chartData avec les noms Reel et Prediction. Recharts peut alors afficher les deux séries dans le même graphique. Cette comparaison permet de visualiser l'écart entre la réalité et la prédiction. Elle peut donc être utilisée comme outil d'analyse afin d'évaluer visuellement la qualité des prédictions produites par le système. Plus généralement, cette architecture permet d'intégrer une composante de Machine Learning dans un dashboard Business Intelligence.

# 107 — Gestion conditionnelle du contenu

Le composant utilise plusieurs conditions React afin d'afficher uniquement les informations correspondant à l'état actuel de l'application. La condition loading && ... affiche le message de chargement lorsque la requête est en cours. La condition error && ... affiche le message d'erreur lorsqu'un problème s'est produit. Enfin, la condition !loading && !error && ... permet d'afficher le contenu principal uniquement lorsque le chargement est terminé et qu'aucune erreur n'est présente. À l'intérieur de cette dernière partie, une autre condition chartData.length > 0 vérifie qu'il existe réellement des données avant d'afficher le graphique. Cette utilisation du rendu conditionnel permet d'éviter les incohérences dans l'interface et d'améliorer l'expérience utilisateur.

# 108 — Conclusion

Le Dashboard Parapharma constitue une fonctionnalité frontend complète permettant de réunir récupération de données, prédiction, visualisation et Business Intelligence. Redux Toolkit centralise la gestion des données grâce au slice parapharma et à l'action asynchrone fetchParapharma. Axios assure la communication avec le backend grâce à une requête HTTP GET. Les états pending, fulfilled et rejected permettent de gérer respectivement le chargement, le succès et l'erreur. React utilise useDispatch() pour déclencher la récupération et useSelector() pour récupérer les résultats depuis Redux. Le hook useEffect() permet de lancer automatiquement la récupération lorsque le dashboard est chargé. Les données real et prediction sont ensuite transformées dans chartData et représentées graphiquement avec Recharts. Enfin, Power BI fournit une couche supplémentaire de Business Intelligence grâce à son intégration dans une iframe. L'ensemble forme donc une architecture moderne dans laquelle chaque technologie possède une responsabilité précise : React pour l'interface, Redux Toolkit pour la gestion d'état, Axios pour la communication avec le backend, Recharts pour la visualisation des prédictions et Power BI pour l'analyse décisionnelle.
