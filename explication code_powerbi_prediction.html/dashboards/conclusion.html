🌐 Web Dashboard — Documentation technique

Cette documentation explique en détail le fonctionnement de l'application React, de React Router, de Redux Toolkit, de l'inscription et de la connexion des utilisateurs, de la protection des routes privées ainsi que du Footer.

Introduction

Cette partie du projet constitue la structure générale de l'application Web.

Elle permet de gérer plusieurs fonctionnalités importantes :

  • la navigation entre les différentes pages ;
  • l'inscription d'un utilisateur ;
  • la connexion d'un utilisateur ;
  • la gestion de l'utilisateur avec Redux Toolkit ;
  • la conservation du token d'authentification ;
  • la protection du Dashboard ;
  • l'affichage des informations de contact ;
  • la présentation des informations relatives au paiement par virement bancaire.

35. RegisterUser.fulfilled 

.addCase(
    RegisterUser.fulfilled,
    (state, action) => {
        state.user =
            action.payload.user;

        state.token =
            action.payload.token;

        state.error = null;
    }
)

Lorsque l'inscription réussit, Redux récupère la réponse du backend.

L'utilisateur est enregistré dans : 

state.user

Le token est enregistré dans : 

state.token

36. Sauvegarde dans localStorage 

localStorage.setItem(
    "user",
    JSON.stringify(
        action.payload.user
    )
);

localStorage.setItem(
    "token",
    action.payload.token
);

Les informations sont également sauvegardées dans le navigateur.

Cela permet à l'application de récupérer l'utilisateur et le token lors d'un nouveau chargement de la page.

37. RegisterUser.rejected 

.addCase(
    RegisterUser.rejected,
    (state, action) => {
        state.error =
            action.payload;
    }
)

Si l'inscription échoue, Redux stocke l'erreur dans : 

state.error

38. LoginUser.fulfilled 

.addCase(
    LoginUser.fulfilled,
    (state, action) => {

        state.user =
            action.payload.user;

        state.token =
            action.payload.token;

        state.error = null;

        localStorage.setItem(
            "user",
            JSON.stringify(
                action.payload.user
            )
        );

        localStorage.setItem(
            "token",
            action.payload.token
        );
    }
)

Lorsque la connexion réussit, Redux récupère l'utilisateur et le token retournés par le backend.

Ces informations sont ensuite enregistrées à la fois dans Redux et dans localStorage.

39. LoginUser.rejected 

.addCase(
    LoginUser.rejected,
    (state, action) => {
        state.error =
            action.payload;
    }
)

Si la connexion échoue, le message ou les données d'erreur sont enregistrés dans state.error.

68. Condition de protection 

if (
    !user &&
    !token &&
    !storedUser
) {
    return (
        <Navigate
            to="/login"
            replace
        />
    );
}

Cette condition vérifie trois éléments :

  • l'utilisateur présent dans Redux ;
  • le token présent dans Redux ;
  • l'utilisateur sauvegardé dans localStorage.

Si ces trois éléments sont absents, l'utilisateur est considéré comme non authentifié et il est redirigé vers la page Login.

69. Redirection vers Login 

<Navigate
    to="/login"
    replace
/>

L'utilisateur non authentifié est envoyé vers : 

/login

La propriété replace permet de remplacer l'entrée actuelle dans l'historique de navigation au lieu d'en ajouter une nouvelle.

70. Autorisation d'accès 

return children;

Si la condition de blocage n'est pas satisfaite, le composant retourne children.

Cela signifie que l'utilisateur est autorisé à accéder au contenu protégé.

87. Rôle de localStorage

localStorage permet de conserver certaines informations dans le navigateur.

Dans votre projet, il est utilisé pour conserver :

  • les informations de l'utilisateur ;
  • le token d'authentification.

Cela permet à l'application de récupérer ces informations après un rechargement de la page.

89. Sécurité et informations bancaires

Le Footer peut informer les visiteurs qu'un paiement par virement bancaire est possible.

Cependant, les informations bancaires complètes ne devraient pas être exposées publiquement dans le code source d'un portfolio ou dans une publication LinkedIn.

Une meilleure organisation consiste à afficher une information générale : 

Paiement par virement bancaire

Les informations bancaires sont disponibles
sur demande après confirmation du projet.

Après accord avec le client, les coordonnées bancaires peuvent être communiquées directement par un moyen privé.
