1. Presentación general de la seguridad

En esta parte del proyecto se ha implementado un sistema completo de autenticación y seguridad de rutas con el objetivo de proteger el acceso a las funcionalidades sensibles de la aplicación. El sistema se basa principalmente en varias tecnologías complementarias: Node.js para la ejecución del backend, Express para la creación de rutas HTTP, Sequelize como ORM para comunicarse con MySQL, bcryptjs para proteger las contraseñas y JSON Web Token, llamado JWT, para gestionar la autenticación de los usuarios. El principio general consiste en permitir que un usuario cree una cuenta con un nombre, una dirección de correo electrónico y una contraseña, y posteriormente pueda iniciar sesión utilizando esta información. Durante el registro, la contraseña original nunca se almacena directamente en la base de datos. Se transforma en un valor hash mediante bcrypt. Durante el inicio de sesión, la contraseña proporcionada por el usuario se compara con el hash almacenado en MySQL. Si la información es correcta, el servidor genera un token JWT que contiene determinada información para identificar al usuario. El frontend recibe posteriormente este token y debe enviarlo cuando accede a rutas protegidas. El middleware autorize recupera el token del encabezado HTTP Authorization, verifica su validez mediante jwt.verify() y la clave secreta JWT_SECRET. Cuando el token es válido, la información decodificada se coloca en req.user y la función next() permite que la solicitud continúe. Si no se proporciona ningún token o si el token es inválido o ha expirado, el servidor bloquea el acceso y devuelve una respuesta HTTP 401 Unauthorized. La arquitectura permite, por tanto, separar claramente varios niveles de seguridad: la gestión de usuarios en MySQL, la protección de contraseñas con bcrypt, la autenticación con JWT y la protección de rutas mediante un middleware de Express.

2. Conexión a MySQL con Sequelize

El primer nivel del sistema corresponde a la conexión entre el servidor Node.js y la base de datos MySQL. Para realizar esta conexión, el proyecto utiliza Sequelize. Sequelize es un ORM que permite manipular una base de datos relacional mediante modelos JavaScript. Esto significa que el desarrollador puede utilizar métodos como findOne() o create() en lugar de escribir directamente todas las consultas SQL. En el archivo config/db.js, la biblioteca Sequelize se importa mediante const { Sequelize, DataTypes } = require("sequelize"). El objeto sequelize se crea posteriormente con el nombre de la base de datos POWERBI_PREDICTION, el usuario MySQL root, una contraseña vacía en este entorno de desarrollo, el host localhost y el dialecto mysql. El parámetro localhost indica que MySQL funciona en la misma máquina que el servidor Node.js, mientras que dialect: "mysql" indica a Sequelize que el sistema de gestión de base de datos utilizado es MySQL. Finalmente, la conexión se exporta mediante module.exports para que pueda ser utilizada por los modelos y controladores de la aplicación. Esta organización permite centralizar la configuración de la base de datos y reutilizar la misma conexión en las diferentes partes del backend. 

const { Sequelize, DataTypes } = require("sequelize");

const sequelize = new Sequelize(
    "POWERBI_PREDICTION",
    "root",
    "",
    {
        host: "localhost",
        dialect: "mysql"
    }
);

module.exports = {
    sequelize,
};

3. Creación del modelo User

El modelo User representa la estructura de los usuarios registrados en la base de datos. El archivo comienza importando DataTypes desde Sequelize, así como la conexión sequelize definida en config/db.js. La función sequelize.define("User", ...) permite crear posteriormente un modelo llamado User. Este modelo contiene cuatro informaciones principales: el identificador, el nombre, el email y la contraseña. El campo id es de tipo entero mediante DataTypes.INTEGER, se incrementa automáticamente con autoIncrement: true y constituye la clave primaria mediante primaryKey: true. El campo name es una cadena de caracteres y allowNull: false indica que el nombre es obligatorio. El campo email también es una cadena de caracteres, es obligatorio y posee la propiedad unique: true. Esto permite impedir que varias cuentas utilicen la misma dirección de correo electrónico. Finalmente, el campo password es obligatorio y se utiliza para almacenar la contraseña en forma de hash. Es muy importante precisar que el valor almacenado en esta columna no debe ser la contraseña original. El controlador utiliza bcrypt antes del almacenamiento para transformar la contraseña en un hash. 

const { DataTypes } = require("sequelize");
const { sequelize } = require("../config/db");

const User = sequelize.define("User", {

    id: {
        type: DataTypes.INTEGER,
        autoIncrement: true,
        primaryKey: true,
    },

    name: {
        type: DataTypes.STRING,
        allowNull: false,
    },

    email: {
        type: DataTypes.STRING,
        allowNull: false,
        unique: true,
    },

    password: {
        type: DataTypes.STRING,
        allowNull: false,
    },

});

module.exports = User;

4. Función Register: registro de un usuario

La función register es responsable del registro de un nuevo usuario. Se declara con async porque realiza varias operaciones asíncronas, incluyendo búsquedas en la base de datos, el hash de la contraseña y la creación del usuario. La información name, email y password se obtiene de req.body, lo que significa que es enviada por el frontend en el cuerpo de la solicitud HTTP. Antes de crear la cuenta, el servidor utiliza User.findOne() con where: { email } para comprobar si ya existe un usuario con esta dirección de correo electrónico. Si existe un usuario, el registro se detiene inmediatamente y el servidor devuelve una respuesta HTTP 400 con el mensaje Email ya utilizado. Esta comprobación es importante porque evita la creación de varias cuentas con la misma dirección de correo electrónico. Si no existe ninguna cuenta, el servidor utiliza bcrypt.hash(password, 10). Esta operación transforma la contraseña original en un valor hash. El número 10 representa el coste computacional utilizado por bcrypt para generar el hash. Por lo tanto, la contraseña original no se almacena directamente en MySQL. Después de este paso, User.create() crea el usuario con su nombre, email y contraseña cifrada mediante hash. Una vez creado el usuario, el servidor genera un token JWT mediante jwt.sign(). El payload del token contiene principalmente el identificador y el email del usuario. El token se firma con la clave secreta situada en process.env.JWT_SECRET y su duración de validez se fija en siete días mediante expiresIn: "7d". Finalmente, el servidor devuelve una respuesta HTTP 201 que contiene el usuario y el token. El frontend puede utilizar este token para futuras solicitudes que requieran autenticación. 

exports.register = async (req, res) => {
    try {

        const { name, email, password } = req.body;

        const exist = await User.findOne({
            where: { email }
        });

        if (exist) {
            return res.status(400).json(
                "Email déjà utilisé"
            );
        }

        const hashedPassword =
            await bcrypt.hash(password, 10);

        const user = await User.create({
            name,
            email,
            password: hashedPassword,
        });

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.status(201).json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

5. Función Login: inicio de sesión del usuario

La función login permite que un usuario registrado inicie sesión en la aplicación. El servidor obtiene el email y la contraseña desde req.body y utiliza User.findOne() para buscar en MySQL al usuario correspondiente a esta dirección de correo electrónico. Si no se encuentra ningún usuario, el servidor devuelve una respuesta HTTP 400 con el mensaje Usuario no encontrado. Si el usuario existe, el servidor no compara directamente dos contraseñas en texto plano. Utiliza bcrypt.compare(password, user.password) para comparar la contraseña introducida con el hash almacenado en la base de datos. Si la comparación devuelve false, el servidor rechaza el inicio de sesión con el mensaje Contraseña incorrecta. Si la contraseña es correcta, el servidor genera un nuevo token JWT mediante jwt.sign(). Al igual que durante el registro, el token contiene el identificador y el email del usuario, está firmado con JWT_SECRET y tiene una duración de siete días. El servidor devuelve posteriormente un objeto JSON que contiene el usuario y el token. El frontend puede conservar este token y enviarlo cuando acceda a funcionalidades protegidas. Esta etapa constituye el mecanismo de autenticación de la aplicación: el usuario demuestra su identidad mediante su email y contraseña y recibe posteriormente un token que permite al servidor reconocer esta autenticación durante las siguientes solicitudes. 

exports.login = async (req, res) => {
    try {

        const { email, password } = req.body;

        const user = await User.findOne({
            where: { email },
        });

        if (!user) {
            return res.status(400).json(
                "Utilisateur introuvable"
            );
        }

        const validPassword =
            await bcrypt.compare(
                password,
                user.password
            );

        if (!validPassword) {
            return res.status(400).json(
                "Mot de passe incorrect"
            );
        }

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

6. Autenticación con JSON Web Token

JSON Web Token, generalmente llamado JWT, se utiliza en este proyecto para gestionar la autenticación entre el frontend y el backend. Después de un registro o inicio de sesión exitoso, el servidor genera un token mediante jwt.sign(). Este token contiene un payload con información que permite identificar al usuario, especialmente su id y su email. El token se firma con process.env.JWT_SECRET. Esta clave secreta es importante porque permite al servidor verificar que el token presentado por el cliente corresponde realmente a un token firmado por el servidor. La clave debe conservarse en una variable de entorno y no debe publicarse directamente en el código fuente. El token también tiene una duración de siete días mediante expiresIn: "7d". Esto significa que un token expirado ya no debe permitir el acceso a las rutas protegidas. JWT permite así evitar enviar la contraseña en cada solicitud. Una vez conectado, el frontend utiliza el token como prueba de autenticación y lo envía al backend cuando desea acceder a una ruta protegida.

Principio importante:

JWT no sustituye a la contraseña y no debe considerarse como la contraseña. Representa una prueba temporal de autenticación creada por el servidor.

7. Middleware autorize: protección de las rutas

El archivo autorize.js contiene un middleware de Express cuyo objetivo es controlar el acceso a las rutas protegidas. El middleware importa primero la biblioteca jsonwebtoken. La función autorize recibe tres parámetros: req, que representa la solicitud HTTP, res, que permite enviar la respuesta al cliente, y next, que permite continuar hacia la siguiente función cuando el usuario está autorizado. El middleware recupera posteriormente el token desde req.headers.authorization. El frontend debe enviar el encabezado con el formato Authorization: Bearer TOKEN. El método split(" ") separa la palabra Bearer del token y el índice [1] recupera únicamente el token. El operador ?. permite evitar un error si el encabezado no existe. El middleware comprueba entonces si el token está presente. Si no se encuentra ningún token, el acceso se rechaza inmediatamente con el estado HTTP 401 y el mensaje Token faltante. Si el token existe, el servidor utiliza jwt.verify() con el token y process.env.JWT_SECRET. Esta operación permite comprobar que el token es válido y que no ha expirado. Si la verificación tiene éxito, la información decodificada se coloca en req.user. Esta etapa es muy útil porque las funciones siguientes pueden conocer ahora al usuario autenticado. Finalmente, next() permite que la solicitud continúe hacia la ruta protegida. Si la verificación falla, por ejemplo porque el token es inválido o ha expirado, la ejecución pasa al bloque catch y el servidor devuelve una respuesta HTTP 401 con el mensaje Token inválido. De esta manera, el middleware constituye una verdadera barrera de seguridad delante de las rutas sensibles. 

const jwt = require("jsonwebtoken");

const autorize = (req, res, next) => {

    const token =
        req.headers.authorization?.split(" ")[1];

    if (!token) {

        return res.status(401).json({
            message: "Token manquant",
        });

    }

    try {

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        req.user = decoded;

        next();

    } catch (error) {

        return res.status(401).json({
            message: "Token invalide",
        });

    }
};

module.exports = autorize;

8. Rutas de registro e inicio de sesión

El archivo de rutas de usuario permite conectar las funciones del controlador con los endpoints HTTP de la aplicación. Express proporciona la función Router(), que permite crear un conjunto de rutas independientes. El archivo importa después las funciones register y login desde el controlador de usuario. La primera ruta es router.post("/register", register). Esto indica que cuando se envía una solicitud HTTP de tipo POST hacia /register, Express ejecuta la función register. Esta función recibe los datos del formulario, verifica el email, realiza el hash de la contraseña, crea el usuario y genera el JWT. La segunda ruta es router.post("/login", login). Cuando se envía una solicitud POST hacia /login, Express ejecuta la función login. Esta función verifica al usuario, compara la contraseña con bcrypt y genera un nuevo token JWT si la información es correcta. Finalmente, module.exports = router permite exportar el router para que pueda ser utilizado en el archivo principal del servidor. Esta separación entre rutas y controladores permite organizar correctamente el backend: las rutas definen las URLs y los métodos HTTP, mientras que los controladores contienen la lógica de negocio. 

const express = require("express");

const router = express.Router();

const { sequelize } = require("../config/db");

const {
    register,
    login,
} = require("../Controllers/userController");

router.post("/register", register);

router.post("/login", login);

module.exports = router;

9. Ruta Admin protegida por JWT

Una ruta especial también permite demostrar concretamente el uso del middleware de seguridad. El router de Express define la ruta GET /admin y coloca el middleware autorize entre la URL y el controlador. El orden es muy importante: cuando llega una solicitud a esta ruta, Express ejecuta primero autorize. El middleware recupera el token JWT del encabezado Authorization, verifica su validez mediante jwt.verify(), coloca la información del usuario en req.user y después llama a next(). Solo después de esta verificación se ejecuta la función de la ruta. Si el token está ausente, el controlador de la ruta nunca se ejecuta y el servidor devuelve un error 401. Si el token es inválido o ha expirado, se aplica el mismo principio. Cuando el token es válido, la ruta puede devolver el mensaje Bienvenido Admin junto con el usuario contenido en req.user. Esta ruta muestra cómo el middleware se convierte en una barrera entre el cliente y una funcionalidad protegida. Sin embargo, es necesario distinguir entre autenticación y autorización: el middleware presentado verifica que el token sea válido e identifica al usuario, pero el código proporcionado aún no comprueba que el usuario tenga realmente un rol de administrador. Para implementar una verdadera autorización basada en roles, sería necesario almacenar también un rol, por ejemplo admin o user, en el modelo de usuario y verificar este rol antes de autorizar el acceso a una ruta estrictamente reservada para administradores. 

const express = require("express");
const router = express.Router();

const autorize =
    require("../middleware/autorize");

/* =========================
   ADMIN ROUTE
========================= */

router.get(
    "/admin",
    autorize,
    (req, res) => {

        res.json({
            message: "Bienvenue Admin",
            user: req.user,
        });

    }
);

module.exports = router;
⚠️ Punto importante:

En el código actual, el middleware verifica que el usuario posea un JWT válido, pero todavía no comprueba que este usuario tenga realmente el rol admin. El nombre de la ruta /admin indica que es una ruta destinada a la administración, pero la seguridad actual corresponde principalmente a una autenticación. Sería necesaria una comprobación adicional del rol para implementar una verdadera autorización de administrador.

10. Funcionamiento completo del sistema

El funcionamiento general de la seguridad comienza cuando el usuario utiliza el frontend para crear una cuenta. El frontend envía una solicitud POST a la ruta /register con el nombre, el email y la contraseña. Express recibe esta solicitud y llama al controlador register. El controlador verifica en MySQL, mediante Sequelize, si el email ya existe. Si la dirección está disponible, bcrypt transforma la contraseña en un hash y Sequelize crea el nuevo usuario en la base de datos. El servidor genera después un JWT firmado con JWT_SECRET y válido durante siete días. Durante el inicio de sesión, el frontend utiliza la ruta /login. El controlador busca al usuario por su email y utiliza bcrypt.compare() para verificar la contraseña. Si la información es correcta, se genera un JWT y se envía al frontend. Para acceder posteriormente a una ruta protegida como /admin, el frontend debe enviar el token en el encabezado Authorization utilizando el formato Bearer TOKEN. Express ejecuta entonces el middleware autorize. Este recupera el token, utiliza jwt.verify() para comprobar su validez y coloca la información del usuario en req.user. Si la verificación tiene éxito, next() permite que la solicitud continúe. Si el token está ausente, es inválido o ha expirado, el acceso se rechaza con un error HTTP 401. Esta arquitectura crea una cadena completa de seguridad desde el frontend hacia Express, después hacia el middleware JWT, el controlador, Sequelize y finalmente MySQL.

11. Las diferentes capas de seguridad

La seguridad de la aplicación se basa en varios mecanismos complementarios y no en una sola tecnología. En primer lugar, Sequelize permite estructurar los datos de los usuarios y comunicarse con MySQL. En segundo lugar, el modelo User impone determinadas restricciones, como la obligatoriedad del nombre, del email y de la contraseña, así como la unicidad de la dirección de correo electrónico. En tercer lugar, bcrypt protege las contraseñas mediante hashing antes de almacenarlas. En cuarto lugar, bcrypt.compare() permite verificar las contraseñas sin necesidad de almacenar la contraseña original. En quinto lugar, JWT proporciona un mecanismo que permite al servidor reconocer a un usuario autenticado. En sexto lugar, JWT_SECRET permite firmar y verificar los tokens. En séptimo lugar, la expiración del token después de siete días limita su duración de validez. En octavo lugar, el middleware autorize constituye una barrera delante de las rutas protegidas. Finalmente, los códigos HTTP como 400, 401 y 500 permiten gestionar diferentes situaciones de error. Todos estos elementos trabajan juntos para crear una arquitectura de autenticación estructurada y más segura que una aplicación que almacenara las contraseñas en texto plano o que dejara todas las rutas accesibles sin ningún control.

12. Gestión de los errores de seguridad

El sistema contempla varias situaciones de error. Cuando un usuario intenta crear una cuenta con una dirección de email que ya está siendo utilizada, el servidor devuelve el estado 400 con el mensaje Email ya utilizado. Cuando un usuario intenta iniciar sesión con una dirección que no existe, el servidor devuelve Usuario no encontrado. Cuando la dirección existe pero la contraseña es incorrecta, bcrypt.compare() devuelve false y el servidor devuelve Contraseña incorrecta. Para las rutas protegidas, si no se envía ningún JWT, el middleware devuelve 401 con Token faltante. Si el JWT es inválido o ha expirado, jwt.verify() genera un error que es capturado por el bloque catch, y el servidor devuelve 401 con Token inválido. Finalmente, los errores inesperados procedentes del servidor o de la base de datos pueden ser capturados por los bloques try/catch de los controladores y devolver un estado 500. Esta gestión permite que el frontend comprenda el resultado de la solicitud y muestre un mensaje adecuado al usuario.

13. Explicación oral para la presentación

Para presentar esta parte ante un jurado, se puede explicar que el proyecto dispone de un sistema de seguridad basado en la autenticación JWT. Cuando un usuario crea una cuenta, el backend recibe su nombre, email y contraseña mediante la ruta /register. Antes de crear la cuenta, Sequelize comprueba en MySQL si el email ya existe. A continuación, la contraseña se cifra mediante hash con bcrypt para que nunca se almacene en texto plano en la base de datos. Después de crear el usuario, el servidor genera un token JWT firmado con una clave secreta almacenada en JWT_SECRET. Durante el inicio de sesión, la ruta /login busca al usuario mediante su email y utiliza bcrypt.compare() para verificar la contraseña. Si las credenciales son correctas, se genera un JWT y se envía al frontend. Para proteger una ruta, por ejemplo /admin, utilizo un middleware llamado autorize. Este middleware recupera el token del encabezado Authorization en forma de Bearer token y utiliza jwt.verify() para comprobar su validez. Si no se proporciona ningún token o si el token es inválido o ha expirado, el servidor devuelve un error 401 y bloquea el acceso. Si el token es válido, la información del usuario se coloca en req.user y next() permite que la solicitud acceda a la ruta protegida. Esta arquitectura permite separar claramente el registro, el inicio de sesión, el hash de las contraseñas, la generación del JWT y la protección de las rutas. Constituye la base de la seguridad backend de mi aplicación.

14. Conclusión

El sistema desarrollado permite implementar una autenticación completa entre el frontend, el backend y la base de datos MySQL. Sequelize garantiza la comunicación con MySQL y permite definir el modelo User. Las rutas Express /register y /login permiten respectivamente crear una cuenta y autenticarse. El uso de bcrypt garantiza que las contraseñas no se almacenen directamente en su forma original. JWT permite después representar el estado de autenticación del usuario durante un período de tiempo limitado. El middleware autorize verifica el token antes de permitir que una solicitud acceda a una ruta protegida. Gracias a jwt.verify(), el servidor puede verificar el token y recuperar la información del usuario en req.user. Las rutas protegidas pueden así controlar el acceso a las funcionalidades sensibles. La arquitectura actual constituye una base sólida de seguridad backend con Node.js, Express, Sequelize, MySQL, bcrypt y JWT. Para una seguridad aún más completa en una verdadera aplicación de producción, esta base puede reforzarse posteriormente con una gestión de roles y permisos, una validación estricta de los datos, protección contra ataques de fuerza bruta, HTTPS, una gestión segura del almacenamiento de tokens y una mejor gestión de la información sensible.
