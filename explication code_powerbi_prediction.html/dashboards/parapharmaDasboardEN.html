# 74 — Managing Parapharma Data with Redux Toolkit and React

In this part of the project, a system for retrieving and visualizing parapharmacy data has been developed using several complementary frontend technologies, including React, Redux Toolkit, Axios, Recharts and Power BI. The main objective of this functionality is to allow the user to access a dashboard dedicated to parapharmacy data. The dashboard combines an integrated Power BI report, the display of real data, prediction values and a chart that visually compares real and predicted values. Unlike the Real Estate dashboard presented previously, this functionality does not contain a button allowing the user to manually enter data. The data is automatically retrieved from the backend when the React component is loaded. Redux Toolkit is used to centralize the state of the Parapharma data, while React is responsible for displaying it in the interface. Axios handles HTTP communication with the Node.js/Express backend. The Recharts library then transforms the received data into a chart. The Power BI report is directly integrated into the page using an iframe. The architecture therefore makes it possible to combine data retrieval, prediction, graphical visualization and Business Intelligence in a single interface.

# 75 — Importing Redux Toolkit and Axios

The Redux file begins by importing createSlice and createAsyncThunk from @reduxjs/toolkit. These two features play different roles in state management. The createSlice() function makes it possible to create a section of the Redux store dedicated to parapharmacy data. It allows the developer to define the slice name, its initial state and the processing associated with the different stages of the asynchronous operation. The createAsyncThunk() function is used to create an asynchronous action intended to perform an operation such as an HTTP request to a server. The file also imports axios using the instruction import axios from "axios". Axios is used here to communicate with the backend API. The combination of Redux Toolkit and Axios therefore makes it possible to separate state management from server communication logic.

# 76 — Creating the fetchParapharma Asynchronous Action

The main action in the Redux file is fetchParapharma. It is created using createAsyncThunk(). The first parameter "parapharma/fetchParapharma" corresponds to the Redux action type. It identifies this operation within the application. The second parameter is an asynchronous function that receives two parameters: _ and thunkAPI. The first parameter is represented by _ because no specific data is required to trigger this action. The thunk is therefore launched without an argument. The second parameter, thunkAPI, provides several Redux Toolkit features, including rejectWithValue(), which is used here to properly transmit an error to the Redux reducer. The function then contains a try/catch block. The try block contains the communication with the backend, while the catch block handles possible errors.

# 77 — GET Request to the Parapharma Backend

Inside the try block, Axios performs an HTTP GET request using the instruction axios.get("http://localhost:3000/parapharma"). This request allows the frontend to request parapharmacy data from the backend. The address http://localhost:3000/parapharma represents the API endpoint used to retrieve the information. The GET method means that the frontend requests data from the server without sending a new dataset to be stored. When the backend responds, the complete response is stored in the constant response. The code then uses return response.data. This instruction returns the data contained in the HTTP response. Redux Toolkit then uses this value as the payload of the fulfilled action if the request succeeds. The frontend can therefore retrieve the data returned by the API and store it in the Redux store.

```
```

# 78 — Error Handling with rejectWithValue

The catch block handles errors that may occur during communication with the backend. The code uses thunkAPI.rejectWithValue() to transmit customized error information to the Redux reducer. The expression error.response?.data?.error || error.message first attempts to retrieve an error message sent directly by the backend. The ?. operator, called optional chaining, allows a property to be accessed without causing another error if one of the previous properties does not exist. If the backend does not provide an error message in error.response.data.error, the code then uses error.message, which corresponds to the message provided by Axios or JavaScript. This value is then transmitted to Redux through rejectWithValue(). The rejected reducer can then retrieve this information using action.payload and store it in the state.

# 79 — Creating the Parapharma Slice

The code then creates the Redux slice using createSlice(). The slice is identified by name: "parapharma". This property indicates that this part of the Redux store is dedicated to the Parapharma functionality. The slice also contains an initialState property that defines the initial state values. This initial state contains five main pieces of information: loading, error, message, rowsInserted and items. The loading property indicates whether data retrieval is currently in progress. It is initialized to false because no request is executed when the store starts. The error property is initialized to null so that a possible error can be stored. message initially contains an empty string. rowsInserted is initialized to zero and will receive the number of rows returned by the backend. Finally, items is initialized with an empty array intended to receive the Parapharma data returned by the API.

# 80 — Managing the Pending State

When the fetchParapharma() action is triggered, Redux Toolkit automatically starts the pending state. The code uses .addCase(fetchParapharma.pending, ...) to define the changes that must be performed during this phase. The first instruction is state.loading = true. This value tells the React application that a data retrieval request is currently in progress. The code also sets state.error = null. This instruction clears any previous error before starting a new retrieval. In the React component, the loading property is then used to display the message "Loading prediction...". The pending state is therefore the first step of the asynchronous cycle: Redux tells the component that the data is not yet available and that the frontend must wait until the backend responds.

```
```

# 81 — Managing the Fulfilled State

When the GET request to the backend succeeds, Redux Toolkit automatically triggers the fulfilled state. The associated reducer then receives the information returned by the thunk in action.payload. The first instruction is state.loading = false, indicating that data retrieval is complete. The code then retrieves the backend message using state.message = action.payload.message. The number of rows is stored using state.rowsInserted = action.payload.rowsInserted. Finally, the main data is stored using state.items = action.payload.data. This last property is particularly important because it contains the data array that will later be used by the React component. The information returned by the backend therefore follows a clear path: it is received by Axios, returned by the thunk, becomes the payload of fulfilled, and is then stored in the Redux store. React can then retrieve these values using useSelector().

```
```

# 82 — Managing the Rejected State

When the Axios request fails, Redux Toolkit triggers the rejected state. This situation can occur when the backend is stopped, when the /parapharma endpoint is incorrect, when a server error occurs, or when a network problem prevents communication. The reducer then uses .addCase(fetchParapharma.rejected, ...). The first instruction sets state.loading back to false, because the request has finished even though it failed. The code then stores the error using state.error = action.payload. The action.payload value corresponds to the information previously transmitted by rejectWithValue(). The React component then retrieves this value and can display the error message using the condition {error && ...}. The Redux Toolkit cycle is therefore fully managed through the three states pending, fulfilled and rejected.

# 83 — Exporting the Parapharma Reducer

At the end of the Redux file, the instruction export default parapharmaSlice.reducer exports the reducer created by createSlice(). This reducer must then be registered in the application's main Redux store. Once registered, the parapharma state becomes accessible within React components. The ParapharmaDashboard component can then use useSelector() to retrieve information from the state and useDispatch() to trigger the fetchParapharma() action. This organization makes it possible to centralize all Parapharma data retrieval and management logic in a dedicated Redux file.

The code uses the instruction const dispatch = useDispatch() to obtain the function used to send actions to Redux. In this component, dispatch is used inside useEffect() with the instruction dispatch(fetchParapharma()). This means that the component asks Redux to execute the asynchronous fetchParapharma action. Redux then automatically triggers the pending cycle, after which the thunk uses Axios to contact the backend. The React component therefore does not communicate directly with the API. It goes through Redux, which makes it possible to centralize the data retrieval logic. This approach makes the code more organized and facilitates application maintenance.

# 88 — Retrieving State with useSelector

The component then retrieves information from the Parapharma slice using useSelector(). The instruction useSelector((state) => state.parapharma) provides access to the entire state associated with this functionality. The code then extracts five properties: loading, error, message, rowsInserted and items. loading indicates whether data retrieval is in progress. error contains a possible error. message contains the message returned by the backend. rowsInserted represents the number of rows returned or processed. Finally, items contains the main Parapharma data array. Through useSelector(), React remains synchronized with Redux. When Redux changes one of these values, the component automatically re-renders and the interface is updated.

# 89 — Automatically Retrieving Data with useEffect

The code then uses the useEffect() hook to automatically trigger data retrieval when the component is loaded. The instruction useEffect(() => { dispatch(fetchParapharma()); }, [dispatch]) indicates that the fetchParapharma() action must be executed after the component renders. With this logic, the user does not need to click a button to request the data. As soon as the Parapharma page is displayed, React triggers the dispatch to Redux. Redux then launches the thunk, which uses Axios to send the GET request to /parapharma. The dependency array contains dispatch. This organization allows React to properly manage the effect and avoid unnecessary execution during subsequent renders. Data loading is therefore automated as soon as the dashboard is opened.

# 101 — Complete Communication Between React, Redux, Axios and the Backend

The complete process begins when the user opens the Parapharma Dashboard. React loads the ParapharmaDashboard component. After rendering, the useEffect() hook automatically triggers dispatch(fetchParapharma()). Redux Toolkit then triggers the pending state and sets loading to true. The fetchParapharma thunk then uses Axios to send an HTTP GET request to http://localhost:3000/parapharma. The backend receives the request, retrieves or processes the Parapharma data, and returns a JSON response. If communication succeeds, the thunk returns response.data. Redux then triggers the fulfilled state and stores the message, number of rows and data in the store. If the request fails, the catch block uses rejectWithValue() and Redux triggers rejected. The component then retrieves the information using useSelector(). The items data is transformed into chartData and then used by Recharts to build the "Real vs Prediction" chart. React automatically updates the interface when the Redux state changes. The Power BI report remains integrated into the page in parallel through the iframe.

# 108 — Conclusion

The Parapharma Dashboard is a complete frontend functionality that combines data retrieval, prediction, visualization and Business Intelligence. Redux Toolkit centralizes data management through the parapharma slice and the asynchronous fetchParapharma action. Axios handles communication with the backend through an HTTP GET request. The pending, fulfilled and rejected states respectively manage loading, success and errors. React uses useDispatch() to trigger data retrieval and useSelector() to retrieve the results from Redux. The useEffect() hook automatically starts data retrieval when the dashboard is loaded. The real and prediction data are then transformed into chartData and graphically represented using Recharts. Finally, Power BI provides an additional Business Intelligence layer through its integration in an iframe. The result is a modern architecture in which each technology has a specific responsibility: React for the interface, Redux Toolkit for state management, Axios for communication with the backend, Recharts for prediction visualization, and Power BI for decision-making analysis.
