# 74 — Gestión de datos de parafarmacia con Redux Toolkit y React

En esta parte del proyecto, se ha desarrollado un sistema para obtener y visualizar datos de parafarmacia utilizando varias tecnologías frontend complementarias, entre ellas React, Redux Toolkit, Axios, Recharts y Power BI. El objetivo principal de esta funcionalidad es permitir al usuario acceder a un dashboard dedicado a los datos de parafarmacia. El dashboard combina un informe de Power BI integrado, la visualización de datos reales, valores de predicción y un gráfico que compara visualmente los valores reales y predichos. A diferencia del dashboard de Real Estate presentado anteriormente, esta funcionalidad no contiene un botón que permita al usuario introducir datos manualmente. Los datos se obtienen automáticamente desde el backend cuando se carga el componente de React. Redux Toolkit se utiliza para centralizar el estado de los datos de Parapharma, mientras que React se encarga de mostrarlos en la interfaz. Axios gestiona la comunicación HTTP con el backend Node.js/Express. La biblioteca Recharts transforma posteriormente los datos recibidos en un gráfico. El informe de Power BI se integra directamente en la página mediante un iframe. Por lo tanto, la arquitectura permite combinar la obtención de datos, la predicción, la visualización gráfica y la Business Intelligence en una única interfaz.

# 75 — Importación de Redux Toolkit y Axios

El archivo de Redux comienza importando createSlice y createAsyncThunk desde @reduxjs/toolkit. Estas dos funcionalidades tienen diferentes funciones en la gestión del estado. La función createSlice() permite crear una sección del store de Redux dedicada a los datos de parafarmacia. Permite al desarrollador definir el nombre del slice, su estado inicial y el procesamiento asociado a las diferentes etapas de la operación asíncrona. La función createAsyncThunk() se utiliza para crear una acción asíncrona destinada a realizar una operación como una solicitud HTTP a un servidor. El archivo también importa axios mediante la instrucción import axios from "axios". Axios se utiliza aquí para comunicarse con la API del backend. La combinación de Redux Toolkit y Axios permite separar la gestión del estado de la lógica de comunicación con el servidor.

# 76 — Creación de la acción asíncrona fetchParapharma

La acción principal del archivo Redux es fetchParapharma. Se crea utilizando createAsyncThunk(). El primer parámetro "parapharma/fetchParapharma" corresponde al tipo de acción de Redux. Identifica esta operación dentro de la aplicación. El segundo parámetro es una función asíncrona que recibe dos parámetros: _ y thunkAPI. El primer parámetro está representado por _ porque no se necesita ningún dato específico para ejecutar esta acción. Por lo tanto, el thunk se inicia sin argumentos. El segundo parámetro, thunkAPI, proporciona varias funcionalidades de Redux Toolkit, incluida rejectWithValue(), que se utiliza aquí para transmitir correctamente un error al reducer de Redux. La función contiene entonces un bloque try/catch. El bloque try contiene la comunicación con el backend, mientras que el bloque catch gestiona los posibles errores.

# 77 — Solicitud GET al backend de Parapharma

Dentro del bloque try, Axios realiza una solicitud HTTP GET utilizando la instrucción axios.get("http://localhost:3000/parapharma"). Esta solicitud permite al frontend solicitar datos de parafarmacia al backend. La dirección http://localhost:3000/parapharma representa el endpoint de la API utilizado para obtener la información. El método GET significa que el frontend solicita datos al servidor sin enviar un nuevo conjunto de datos para almacenarlo. Cuando el backend responde, la respuesta completa se almacena en la constante response. El código utiliza entonces return response.data. Esta instrucción devuelve los datos contenidos en la respuesta HTTP. Redux Toolkit utiliza posteriormente este valor como payload de la acción fulfilled si la solicitud tiene éxito. De esta manera, el frontend puede recuperar los datos devueltos por la API y almacenarlos en el store de Redux.

# 78 — Gestión de errores con rejectWithValue

El bloque catch gestiona los errores que pueden producirse durante la comunicación con el backend. El código utiliza thunkAPI.rejectWithValue() para transmitir información de error personalizada al reducer de Redux. La expresión error.response?.data?.error || error.message intenta primero recuperar un mensaje de error enviado directamente por el backend. El operador ?., llamado encadenamiento opcional, permite acceder a una propiedad sin provocar otro error si alguna de las propiedades anteriores no existe. Si el backend no proporciona un mensaje de error en error.response.data.error, el código utiliza entonces error.message, que corresponde al mensaje proporcionado por Axios o JavaScript. Este valor se transmite posteriormente a Redux mediante rejectWithValue(). El reducer rejected puede recuperar esta información utilizando action.payload y almacenarla en el estado.

# 79 — Creación del slice de Parapharma

A continuación, el código crea el slice de Redux utilizando createSlice(). El slice se identifica mediante name: "parapharma". Esta propiedad indica que esta parte del store de Redux está dedicada a la funcionalidad de Parapharma. El slice también contiene una propiedad initialState que define los valores iniciales del estado. Este estado inicial contiene cinco elementos principales de información: loading, error, message, rowsInserted e items. La propiedad loading indica si la obtención de datos está actualmente en progreso. Se inicializa en false porque no se ejecuta ninguna solicitud cuando se inicia el store. La propiedad error se inicializa en null para poder almacenar un posible error. message contiene inicialmente una cadena vacía. rowsInserted se inicializa en cero y recibirá el número de filas devueltas por el backend. Finalmente, items se inicializa con un array vacío destinado a recibir los datos de Parapharma devueltos por la API.

# 80 — Gestión del estado Pending

Cuando se ejecuta la acción fetchParapharma(), Redux Toolkit inicia automáticamente el estado pending. El código utiliza .addCase(fetchParapharma.pending, ...) para definir los cambios que deben realizarse durante esta fase. La primera instrucción es state.loading = true. Este valor indica a la aplicación React que una solicitud de obtención de datos está actualmente en progreso. El código también establece state.error = null. Esta instrucción elimina cualquier error anterior antes de iniciar una nueva obtención. En el componente React, la propiedad loading se utiliza posteriormente para mostrar el mensaje "Loading prediction...". El estado pending constituye, por tanto, el primer paso del ciclo asíncrono: Redux informa al componente de que los datos todavía no están disponibles y que el frontend debe esperar hasta que el backend responda.

# 81 — Gestión del estado Fulfilled

Cuando la solicitud GET al backend tiene éxito, Redux Toolkit activa automáticamente el estado fulfilled. El reducer asociado recibe entonces la información devuelta por el thunk en action.payload. La primera instrucción es state.loading = false, lo que indica que la obtención de datos ha terminado. A continuación, el código recupera el mensaje del backend mediante state.message = action.payload.message. El número de filas se almacena utilizando state.rowsInserted = action.payload.rowsInserted. Finalmente, los datos principales se almacenan mediante state.items = action.payload.data. Esta última propiedad es especialmente importante porque contiene el array de datos que posteriormente será utilizado por el componente React. La información devuelta por el backend sigue, por tanto, un recorrido claro: Axios la recibe, el thunk la devuelve, se convierte en el payload de fulfilled y luego se almacena en el store de Redux. React puede posteriormente recuperar estos valores mediante useSelector().

# 82 — Gestión del estado Rejected

Cuando la solicitud de Axios falla, Redux Toolkit activa el estado rejected. Esta situación puede producirse cuando el backend está detenido, cuando el endpoint /parapharma es incorrecto, cuando ocurre un error en el servidor o cuando un problema de red impide la comunicación. El reducer utiliza entonces .addCase(fetchParapharma.rejected, ...). La primera instrucción vuelve a establecer state.loading en false, porque la solicitud ha terminado aunque haya fallado. El código almacena entonces el error mediante state.error = action.payload. El valor de action.payload corresponde a la información transmitida anteriormente mediante rejectWithValue(). El componente React recupera posteriormente este valor y puede mostrar el mensaje de error mediante la condición {error && ...}. Por lo tanto, el ciclo de Redux Toolkit se gestiona completamente mediante los tres estados pending, fulfilled y rejected.

Redux Toolkit inicia entonces el estado pending y establece loading en true. El thunk utiliza Axios para enviar una solicitud GET a /parapharma. El backend procesa la solicitud y devuelve la información requerida. Si la respuesta es correcta, Redux activa fulfilled. El mensaje se almacena en message, el número de filas en rowsInserted y los datos en items. React recupera esta información mediante useSelector(). Cada elemento contiene, en particular, un valor real y un valor de predicción. El componente transforma entonces esta información en chartData. Recharts utiliza estos datos para construir un gráfico que compara Real y Prediction. Si se produce un error durante la solicitud, Redux activa rejected y el error se muestra en la interfaz. El sistema sigue, por tanto, automáticamente el flujo de datos desde el backend hasta su representación final.

# 106 — Diferencia entre los datos reales y los datos de predicción

Una parte esencial de este dashboard es la comparación entre dos tipos de valores: valores reales y valores de predicción. En los datos recibidos desde el backend, la propiedad real representa el valor observado o real. La propiedad prediction representa el valor producido por el modelo de predicción. El componente transforma estas dos propiedades en chartData utilizando los nombres Reel y Prediction. Recharts puede entonces mostrar ambas series en el mismo gráfico. Esta comparación permite visualizar la diferencia entre la realidad y la predicción. Por lo tanto, puede utilizarse como una herramienta de análisis para evaluar visualmente la calidad de las predicciones producidas por el sistema. De manera más general, esta arquitectura permite integrar un componente de Machine Learning en un dashboard de Business Intelligence.

# 107 — Gestión condicional del contenido

El componente utiliza varias condiciones de React para mostrar únicamente la información correspondiente al estado actual de la aplicación. La condición loading && ... muestra el mensaje de carga mientras la solicitud está en progreso. La condición error && ... muestra el mensaje de error cuando se produce un problema. Finalmente, la condición !loading && !error && ... muestra el contenido principal únicamente cuando la carga ha terminado y no existe ningún error. Dentro de esta última sección, otra condición chartData.length > 0 comprueba que realmente existan datos antes de mostrar el gráfico. Este uso del renderizado condicional ayuda a evitar inconsistencias en la interfaz y mejora la experiencia del usuario.

# 108 — Conclusión

El Parapharma Dashboard es una funcionalidad frontend completa que combina obtención de datos, predicción, visualización y Business Intelligence. Redux Toolkit centraliza la gestión de datos mediante el slice parapharma y la acción asíncrona fetchParapharma. Axios gestiona la comunicación con el backend mediante una solicitud HTTP GET. Los estados pending, fulfilled y rejected gestionan respectivamente la carga, el éxito y los errores. React utiliza useDispatch() para activar la obtención de datos y useSelector() para recuperar los resultados desde Redux. El hook useEffect() inicia automáticamente la obtención de datos cuando se carga el dashboard. Los datos real y prediction se transforman posteriormente en chartData y se representan gráficamente mediante Recharts. Finalmente, Power BI proporciona una capa adicional de Business Intelligence mediante su integración en un iframe. El resultado es una arquitectura moderna en la que cada tecnología tiene una responsabilidad específica: React para la interfaz, Redux Toolkit para la gestión del estado, Axios para la comunicación con el backend, Recharts para la visualización de las predicciones y Power BI para el análisis y la toma de decisiones.
