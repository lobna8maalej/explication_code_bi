💊 Parapharma Dashboard — Explicação do código

Documentação técnica que explica como Redux Toolkit, React, Axios, Recharts e Power BI trabalham juntos para a obtenção, previsão e visualização de dados de parafarmácia.

# 74 — Gerenciamento de dados de Parapharma com Redux Toolkit e React

Nesta parte do projeto, foi desenvolvido um sistema para obter e visualizar dados de parafarmácia utilizando várias tecnologias complementares de frontend, incluindo React, Redux Toolkit, Axios, Recharts e Power BI. O principal objetivo dessa funcionalidade é permitir que o usuário acesse um dashboard dedicado aos dados de parafarmácia. O dashboard combina um relatório do Power BI integrado, a exibição de dados reais, valores de previsão e um gráfico que compara visualmente os valores reais e previstos. Diferentemente do dashboard de Real Estate apresentado anteriormente, essa funcionalidade não possui um botão que permita ao usuário inserir dados manualmente. Os dados são obtidos automaticamente do backend quando o componente React é carregado. Redux Toolkit é utilizado para centralizar o estado dos dados de Parapharma, enquanto React é responsável por exibi-los na interface. Axios gerencia a comunicação HTTP com o backend Node.js/Express. A biblioteca Recharts transforma os dados recebidos em um gráfico. O relatório do Power BI é integrado diretamente à página usando um iframe. Dessa forma, a arquitetura permite combinar obtenção de dados, previsão, visualização gráfica e Business Intelligence em uma única interface.

# 75 — Importação do Redux Toolkit e Axios

O arquivo Redux começa importando createSlice e createAsyncThunk de @reduxjs/toolkit. Esses dois recursos desempenham funções diferentes no gerenciamento do estado. A função createSlice() permite criar uma seção do store Redux dedicada aos dados de parafarmácia. Ela permite definir o nome do slice, seu estado inicial e o processamento associado às diferentes etapas da operação assíncrona. A função createAsyncThunk() é utilizada para criar uma ação assíncrona destinada a executar uma operação, como uma requisição HTTP para um servidor. O arquivo também importa axios usando a instrução import axios from "axios". Axios é utilizado aqui para se comunicar com a API do backend. A combinação de Redux Toolkit e Axios permite separar o gerenciamento do estado da lógica de comunicação com o servidor.

# 76 — Criação da ação assíncrona fetchParapharma

A principal ação do arquivo Redux é fetchParapharma. Ela é criada utilizando createAsyncThunk(). O primeiro parâmetro "parapharma/fetchParapharma" corresponde ao tipo da ação Redux. Ele identifica essa operação dentro da aplicação. O segundo parâmetro é uma função assíncrona que recebe dois parâmetros: _ e thunkAPI. O primeiro parâmetro é representado por _ porque nenhum dado específico é necessário para executar essa ação. Portanto, o thunk é executado sem argumentos. O segundo parâmetro, thunkAPI, fornece vários recursos do Redux Toolkit, incluindo rejectWithValue(), que é utilizado aqui para transmitir corretamente um erro ao reducer do Redux. A função contém então um bloco try/catch. O bloco try contém a comunicação com o backend, enquanto o bloco catch trata possíveis erros.

# 77 — Requisição GET ao backend de Parapharma

Dentro do bloco try, o Axios realiza uma requisição HTTP GET usando a instrução axios.get("http://localhost:3000/parapharma"). Essa requisição permite que o frontend solicite dados de parafarmácia ao backend. O endereço http://localhost:3000/parapharma representa o endpoint da API utilizado para obter as informações. O método GET significa que o frontend solicita dados ao servidor sem enviar um novo conjunto de dados para ser armazenado. Quando o backend responde, a resposta completa é armazenada na constante response. O código então utiliza return response.data. Essa instrução retorna os dados contidos na resposta HTTP. O Redux Toolkit utiliza esse valor como payload da ação fulfilled quando a requisição é bem-sucedida. Dessa forma, o frontend pode recuperar os dados retornados pela API e armazená-los no store do Redux.

# 78 — Tratamento de erros com rejectWithValue

O bloco catch trata os erros que podem ocorrer durante a comunicação com o backend. O código utiliza thunkAPI.rejectWithValue() para transmitir informações de erro personalizadas ao reducer do Redux. A expressão error.response?.data?.error || error.message tenta primeiro obter uma mensagem de erro enviada diretamente pelo backend. O operador ?., chamado de optional chaining, permite acessar uma propriedade sem causar outro erro caso alguma das propriedades anteriores não exista. Se o backend não fornecer uma mensagem de erro em error.response.data.error, o código utiliza então error.message, que corresponde à mensagem fornecida pelo Axios ou pelo JavaScript. Esse valor é então transmitido ao Redux através de rejectWithValue(). O reducer rejected pode recuperar essas informações utilizando action.payload e armazená-las no estado.

# 79 — Criação do slice de Parapharma

O código então cria o slice do Redux utilizando createSlice(). O slice é identificado por name: "parapharma". Essa propriedade indica que essa parte do store Redux é dedicada à funcionalidade de Parapharma. O slice também contém uma propriedade initialState que define os valores iniciais do estado. Esse estado inicial contém cinco informações principais: loading, error, message, rowsInserted e items. A propriedade loading indica se a obtenção dos dados está em andamento. Ela é inicializada como false porque nenhuma requisição é executada quando o store é iniciado. A propriedade error é inicializada como null para armazenar um possível erro. message inicialmente contém uma string vazia. rowsInserted é inicializada com zero e receberá o número de linhas retornadas pelo backend. Finalmente, items é inicializado com um array vazio destinado a receber os dados de Parapharma retornados pela API.

# 80 — Gerenciamento do estado Pending

Quando a ação fetchParapharma() é executada, o Redux Toolkit inicia automaticamente o estado pending. O código utiliza .addCase(fetchParapharma.pending, ...) para definir as alterações que devem ser realizadas durante essa fase. A primeira instrução é state.loading = true. Esse valor informa à aplicação React que uma requisição de obtenção de dados está em andamento. O código também define state.error = null. Essa instrução limpa qualquer erro anterior antes de iniciar uma nova obtenção de dados. No componente React, a propriedade loading é então utilizada para exibir a mensagem "Loading prediction...". O estado pending é, portanto, a primeira etapa do ciclo assíncrono: o Redux informa ao componente que os dados ainda não estão disponíveis e que o frontend deve aguardar até que o backend responda.

# 81 — Gerenciamento do estado Fulfilled

Quando a requisição GET ao backend é bem-sucedida, o Redux Toolkit ativa automaticamente o estado fulfilled. O reducer associado recebe então as informações retornadas pelo thunk em action.payload. A primeira instrução é state.loading = false, indicando que a obtenção dos dados foi concluída. O código então recupera a mensagem do backend utilizando state.message = action.payload.message. O número de linhas é armazenado utilizando state.rowsInserted = action.payload.rowsInserted. Finalmente, os dados principais são armazenados utilizando state.items = action.payload.data. Essa última propriedade é particularmente importante porque contém o array de dados que será posteriormente utilizado pelo componente React. As informações retornadas pelo backend seguem, portanto, um fluxo claro: são recebidas pelo Axios, retornadas pelo thunk, tornam-se o payload de fulfilled e depois são armazenadas no store Redux. React pode então recuperar esses valores utilizando useSelector().

# 82 — Gerenciamento do estado Rejected

Quando a requisição do Axios falha, o Redux Toolkit ativa o estado rejected. Essa situação pode ocorrer quando o backend está parado, quando o endpoint /parapharma está incorreto, quando ocorre um erro no servidor ou quando um problema de rede impede a comunicação. O reducer utiliza então .addCase(fetchParapharma.rejected, ...). A primeira instrução define novamente state.loading como false, porque a requisição terminou, mesmo tendo falhado. O código então armazena o erro utilizando state.error = action.payload. O valor de action.payload corresponde às informações anteriormente transmitidas por rejectWithValue(). O componente React recupera então esse valor e pode exibir a mensagem de erro utilizando a condição {error && ...}. Dessa forma, o ciclo do Redux Toolkit é totalmente gerenciado pelos três estados pending, fulfilled e rejected.

# 83 — Exportação do reducer de Parapharma

No final do arquivo Redux, a instrução export default parapharmaSlice.reducer exporta o reducer criado por createSlice(). Esse reducer deve então ser registrado no store principal do Redux da aplicação. Depois de registrado, o estado parapharma fica disponível nos componentes React. O componente ParapharmaDashboard pode então utilizar useSelector() para recuperar informações do estado e useDispatch() para executar a ação.
