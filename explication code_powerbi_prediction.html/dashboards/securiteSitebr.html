1. Visão geral da segurança

Nesta parte do projeto foi implementado um sistema completo de autenticação e segurança de rotas com o objetivo de proteger o acesso às funcionalidades sensíveis da aplicação. O sistema é baseado principalmente em várias tecnologias complementares: Node.js para a execução do backend, Express para a criação das rotas HTTP, Sequelize como ORM para comunicação com o MySQL, bcryptjs para proteção das senhas e JSON Web Token, chamado JWT, para gerenciamento da autenticação dos usuários. O princípio geral consiste em permitir que um usuário crie uma conta com nome, endereço de e-mail e senha e, posteriormente, possa fazer login utilizando essas informações. Durante o cadastro, a senha original nunca é armazenada diretamente no banco de dados. Ela é transformada em um valor hash utilizando bcrypt. Durante o login, a senha fornecida pelo usuário é comparada com o hash armazenado no MySQL. Se as informações estiverem corretas, o servidor gera um token JWT que contém determinadas informações para identificar o usuário. O frontend recebe esse token posteriormente e deve enviá-lo quando acessar rotas protegidas. O middleware autorize recupera o token do cabeçalho HTTP Authorization, verifica sua validade por meio de jwt.verify() e da chave secreta JWT_SECRET. Quando o token é válido, as informações decodificadas são colocadas em req.user e a função next() permite que a requisição continue. Se nenhum token for fornecido ou se o token for inválido ou tiver expirado, o servidor bloqueia o acesso e retorna uma resposta HTTP 401 Unauthorized. A arquitetura permite, portanto, separar claramente vários níveis de segurança: gerenciamento dos usuários no MySQL, proteção das senhas com bcrypt, autenticação com JWT e proteção das rotas por meio de um middleware do Express.

2. Conexão com MySQL usando Sequelize

O primeiro nível do sistema corresponde à conexão entre o servidor Node.js e o banco de dados MySQL. Para realizar essa conexão, o projeto utiliza Sequelize. Sequelize é um ORM que permite manipular um banco de dados relacional por meio de modelos JavaScript. Isso significa que o desenvolvedor pode utilizar métodos como findOne() ou create() em vez de escrever diretamente todas as consultas SQL. No arquivo config/db.js, a biblioteca Sequelize é importada por meio de const { Sequelize, DataTypes } = require("sequelize"). O objeto sequelize é criado posteriormente com o nome do banco de dados POWERBI_PREDICTION, o usuário do MySQL root, uma senha vazia neste ambiente de desenvolvimento, o host localhost e o dialeto mysql. O parâmetro localhost indica que o MySQL está funcionando na mesma máquina que o servidor Node.js, enquanto dialect: "mysql" indica ao Sequelize que o sistema de gerenciamento de banco de dados utilizado é o MySQL. Finalmente, a conexão é exportada por meio de module.exports para que possa ser utilizada pelos modelos e controladores da aplicação. Essa organização permite centralizar a configuração do banco de dados e reutilizar a mesma conexão nas diferentes partes do backend. 

const { Sequelize, DataTypes } = require("sequelize");

const sequelize = new Sequelize(
    "POWERBI_PREDICTION",
    "root",
    "",
    {
        host: "localhost",
        dialect: "mysql"
    }
);

module.exports = {
    sequelize,
};

3. Criação do modelo User

O modelo User representa a estrutura dos usuários cadastrados no banco de dados. O arquivo começa importando DataTypes do Sequelize, assim como a conexão sequelize definida em config/db.js. A função sequelize.define("User", ...) permite posteriormente criar um modelo chamado User. Esse modelo contém quatro informações principais: identificador, nome, e-mail e senha. O campo id é do tipo inteiro utilizando DataTypes.INTEGER, é incrementado automaticamente com autoIncrement: true e constitui a chave primária por meio de primaryKey: true. O campo name é uma string e allowNull: false indica que o nome é obrigatório. O campo email também é uma string, é obrigatório e possui a propriedade unique: true. Isso permite impedir que várias contas utilizem o mesmo endereço de e-mail. Por fim, o campo password é obrigatório e é utilizado para armazenar a senha em formato de hash. É muito importante esclarecer que o valor armazenado nessa coluna não deve ser a senha original. O controlador utiliza bcrypt antes do armazenamento para transformar a senha em um hash. 

const { DataTypes } = require("sequelize");
const { sequelize } = require("../config/db");

const User = sequelize.define("User", {

    id: {
        type: DataTypes.INTEGER,
        autoIncrement: true,
        primaryKey: true,
    },

    name: {
        type: DataTypes.STRING,
        allowNull: false,
    },

    email: {
        type: DataTypes.STRING,
        allowNull: false,
        unique: true,
    },

    password: {
        type: DataTypes.STRING,
        allowNull: false,
    },

});

module.exports = User;

4. Função Register: cadastro de um usuário

A função register é responsável pelo cadastro de um novo usuário. Ela é declarada com async porque realiza várias operações assíncronas, incluindo buscas no banco de dados, o hash da senha e a criação do usuário. As informações name, email e password são obtidas de req.body, o que significa que são enviadas pelo frontend no corpo da requisição HTTP. Antes de criar a conta, o servidor utiliza User.findOne() com where: { email } para verificar se já existe um usuário com esse endereço de e-mail. Se existir um usuário, o cadastro é interrompido imediatamente e o servidor retorna uma resposta HTTP 400 com a mensagem E-mail já utilizado. Essa verificação é importante porque evita a criação de várias contas com o mesmo endereço de e-mail. Se nenhuma conta existir, o servidor utiliza bcrypt.hash(password, 10). Essa operação transforma a senha original em um valor hash. O número 10 representa o custo computacional utilizado pelo bcrypt para gerar o hash. Portanto, a senha original não é armazenada diretamente no MySQL. Depois dessa etapa, User.create() cria o usuário com seu nome, e-mail e senha transformada em hash. Depois que o usuário é criado, o servidor gera um token JWT utilizando jwt.sign(). O payload do token contém principalmente o identificador e o e-mail do usuário. O token é assinado com a chave secreta localizada em process.env.JWT_SECRET e seu período de validade é definido em sete dias por meio de expiresIn: "7d". Finalmente, o servidor retorna uma resposta HTTP 201 contendo o usuário e o token. O frontend pode utilizar esse token para futuras requisições que exigem autenticação. 

exports.register = async (req, res) => {
    try {

        const { name, email, password } = req.body;

        const exist = await User.findOne({
            where: { email }
        });

        if (exist) {
            return res.status(400).json(
                "E-mail já utilizado"
            );
        }

        const hashedPassword =
            await bcrypt.hash(password, 10);

        const user = await User.create({
            name,
            email,
            password: hashedPassword,
        });

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.status(201).json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

5. Função Login: login do usuário

A função login permite que um usuário cadastrado faça login na aplicação. O servidor obtém o e-mail e a senha de req.body e utiliza User.findOne() para buscar no MySQL o usuário correspondente a esse endereço de e-mail. Se nenhum usuário for encontrado, o servidor retorna uma resposta HTTP 400 com a mensagem Usuário não encontrado. Se o usuário existir, o servidor não compara diretamente duas senhas em texto puro. Ele utiliza bcrypt.compare(password, user.password) para comparar a senha informada com o hash armazenado no banco de dados. Se a comparação retornar false, o servidor rejeita o login com a mensagem Senha incorreta. Se a senha estiver correta, o servidor gera um novo token JWT utilizando jwt.sign(). Assim como no cadastro, o token contém o identificador e o e-mail do usuário, é assinado com JWT_SECRET e possui validade de sete dias. O servidor retorna posteriormente um objeto JSON contendo o usuário e o token. O frontend pode armazenar esse token e enviá-lo ao acessar funcionalidades protegidas. Essa etapa constitui o mecanismo de autenticação da aplicação: o usuário comprova sua identidade por meio do e-mail e da senha e, posteriormente, recebe um token que permite ao servidor reconhecer essa autenticação nas próximas requisições. 

exports.login = async (req, res) => {
    try {

        const { email, password } = req.body;

        const user = await User.findOne({
            where: { email },
        });

        if (!user) {
            return res.status(400).json(
                "Usuário não encontrado"
            );
        }

        const validPassword =
            await bcrypt.compare(
                password,
                user.password
            );

        if (!validPassword) {
            return res.status(400).json(
                "Senha incorreta"
            );
        }

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

6. Autenticação com JSON Web Token

JSON Web Token, geralmente chamado de JWT, é utilizado neste projeto para gerenciar a autenticação entre o frontend e o backend. Após um cadastro ou login bem-sucedido, o servidor gera um token utilizando jwt.sign(). Esse token contém um payload com informações que permitem identificar o usuário, especialmente seu id e seu email. O token é assinado com process.env.JWT_SECRET. Essa chave secreta é importante porque permite ao servidor verificar se o token apresentado pelo cliente corresponde realmente a um token assinado pelo servidor. A chave deve ser mantida em uma variável de ambiente e não deve ser publicada diretamente no código-fonte. O token também possui validade de sete dias por meio de expiresIn: "7d". Isso significa que um token expirado não deve mais permitir o acesso às rotas protegidas. Dessa forma, o JWT permite evitar o envio da senha em todas as requisições. Depois de conectado, o frontend utiliza o token como prova de autenticação e o envia ao backend quando deseja acessar uma rota protegida.

Princípio importante:

JWT não substitui a senha e não deve ser considerado como a senha. Ele representa uma prova temporária de autenticação criada pelo servidor.

7. Middleware autorize: proteção das rotas

O arquivo autorize.js contém um middleware do Express cujo objetivo é controlar o acesso às rotas protegidas. O middleware importa primeiro a biblioteca jsonwebtoken. A função autorize recebe três parâmetros: req, que representa a requisição HTTP; res, que permite enviar a resposta ao cliente; e next, que permite continuar para a próxima função quando o usuário está autorizado. O middleware recupera posteriormente o token de req.headers.authorization. O frontend deve enviar o cabeçalho no formato Authorization: Bearer TOKEN. O método split(" ") separa a palavra Bearer do token e o índice [1] recupera apenas o token. O operador ?. permite evitar um erro caso o cabeçalho não exista. O middleware verifica então se o token está presente. Se nenhum token for encontrado, o acesso é imediatamente rejeitado com o status HTTP 401 e a mensagem Token ausente. Se o token existir, o servidor utiliza jwt.verify() com o token e process.env.JWT_SECRET. Essa operação permite verificar se o token é válido e se não expirou. Se a verificação for bem-sucedida, as informações decodificadas são colocadas em req.user. Essa etapa é muito útil porque as funções seguintes podem conhecer o usuário autenticado. Finalmente, next() permite que a requisição continue até a rota protegida. Se a verificação falhar, por exemplo porque o token é inválido ou expirou, a execução passa para o bloco catch e o servidor retorna uma resposta HTTP 401 com a mensagem Token inválido. Dessa forma, o middleware constitui uma verdadeira barreira de segurança diante das rotas sensíveis. 

const jwt = require("jsonwebtoken");

const autorize = (req, res, next) => {

    const token =
        req.headers.authorization?.split(" ")[1];

    if (!token) {

        return res.status(401).json({
            message: "Token ausente",
        });

    }

    try {

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        req.user = decoded;

        next();

    } catch (error) {

        return res.status(401).json({
            message: "Token inválido",
        });

    }
};

module.exports = autorize;

8. Rotas de cadastro e login

O arquivo de rotas do usuário permite conectar as funções do controlador aos endpoints HTTP da aplicação. O Express fornece a função Router(), que permite criar um conjunto de rotas independentes. O arquivo importa posteriormente as funções register e login do controlador de usuário. A primeira rota é router.post("/register", register). Isso significa que, quando uma requisição HTTP do tipo POST é enviada para /register, o Express executa a função register. Essa função recebe os dados do formulário, verifica o e-mail, realiza o hash da senha, cria o usuário e gera o JWT. A segunda rota é router.post("/login", login). Quando uma requisição POST é enviada para /login, o Express executa a função login. Essa função verifica o usuário, compara a senha com bcrypt e gera um novo token JWT se as informações estiverem corretas. Finalmente, module.exports = router permite exportar o router para que possa ser utilizado no arquivo principal do servidor. Essa separação entre rotas e controladores permite organizar corretamente o backend: as rotas definem as URLs e os métodos HTTP, enquanto os controladores contêm a lógica de negócio. 

const express = require("express");

const router = express.Router();

const { sequelize } = require("../config/db");

const {
    register,
    login,
} = require("../Controllers/userController");

router.post("/register", register);

router.post("/login", login);

module.exports = router;

9. Rota Admin protegida por JWT

Uma rota especial também permite demonstrar concretamente o uso do middleware de segurança. O router do Express define a rota GET /admin e coloca o middleware autorize entre a URL e o controlador. A ordem é muito importante: quando uma requisição chega a essa rota, o Express executa primeiro autorize. O middleware recupera o token JWT do cabeçalho Authorization, verifica sua validade por meio de jwt.verify(), coloca as informações do usuário em req.user e depois chama next(). Somente após essa verificação a função da rota é executada. Se o token estiver ausente, o controlador da rota nunca será executado e o servidor retornará um erro 401. Se o token for inválido ou tiver expirado, o mesmo princípio será aplicado. Quando o token é válido, a rota pode retornar a mensagem Bem-vindo Admin junto com o usuário contido em req.user. Essa rota mostra como o middleware se transforma em uma barreira entre o cliente e uma funcionalidade protegida. No entanto, é necessário distinguir autenticação de autorização: o middleware apresentado verifica se o token é válido e identifica o usuário, mas o código fornecido ainda não verifica se o usuário realmente possui a função de administrador. Para implementar uma verdadeira autorização baseada em funções, seria necessário também armazenar uma função, por exemplo admin ou user, no modelo de usuário e verificar essa função antes de autorizar o acesso a uma rota estritamente reservada aos administradores. 

const express = require("express");
const router = express.Router();

const autorize =
    require("../middleware/autorize");

/* =========================
   ADMIN ROUTE
========================= */

router.get(
    "/admin",
    autorize,
    (req, res) => {

        res.json({
            message: "Bem-vindo Admin",
            user: req.user,
        });

    }
);

module.exports = router;
⚠️ Ponto importante:

No código atual, o middleware verifica se o usuário possui um JWT válido, mas ainda não verifica se esse usuário realmente possui a função admin. O nome da rota /admin indica que ela é destinada à administração, mas a segurança atual corresponde principalmente a uma autenticação. Seria necessária uma verificação adicional da função para implementar uma verdadeira autorização de administrador.

10. Funcionamento completo do sistema

O funcionamento geral da segurança começa quando o usuário utiliza o frontend para criar uma conta. O frontend envia uma requisição POST para a rota /register com o nome, o e-mail e a senha. O Express recebe essa requisição e chama o controlador register. O controlador verifica no MySQL, por meio do Sequelize, se o e-mail já existe. Se o endereço estiver disponível, o bcrypt transforma a senha em um hash e o Sequelize cria o novo usuário no banco de dados. O servidor gera então um JWT assinado com JWT_SECRET e válido por sete dias. Durante o login, o frontend utiliza a rota /login. O controlador procura o usuário pelo e-mail e utiliza bcrypt.compare() para verificar a senha. Se as informações estiverem corretas, um JWT é gerado e enviado ao frontend. Para acessar posteriormente uma rota protegida como /admin, o frontend deve enviar o token no cabeçalho Authorization utilizando o formato Bearer TOKEN. O Express executa então o middleware autorize. Ele recupera o token, utiliza jwt.verify() para verificar sua validade e coloca as informações do usuário em req.user. Se a verificação for bem-sucedida, next() permite que a requisição continue. Se o token estiver ausente, for inválido ou tiver expirado, o acesso será rejeitado com um erro HTTP 401. Essa arquitetura cria uma cadeia completa de segurança desde o frontend até o Express, depois para o middleware JWT, o controlador, o Sequelize e finalmente o MySQL.

Frontend ↓ POST /register ↓ Express Router ↓ register() ↓ Verificação do e-mail ↓ bcrypt.hash() ↓ MySQL / Sequelize ↓ Criação de User ↓ jwt.sign() ↓ JWT ↓ Frontend ↓ Authorization: Bearer TOKEN ↓ GET /admin ↓ autorize() ↓ jwt.verify() ↓ ┌──────────────────────────┐ │ Token válido? │ └──────────────────────────┘ ↓ ↓ NÃO SIM ↓ ↓ 401 req.user ↓ next() ↓ /admin ↓ Resposta

11. As diferentes camadas de segurança

A segurança da aplicação é baseada em vários mecanismos complementares e não em uma única tecnologia. Em primeiro lugar, o Sequelize permite estruturar os dados dos usuários e se comunicar com o MySQL. Em segundo lugar, o modelo User impõe determinadas restrições, como a obrigatoriedade do nome, do e-mail e da senha, assim como a unicidade do endereço de e-mail. Em terceiro lugar, o bcrypt protege as senhas por meio de hashing antes de armazená-las. Em quarto lugar, bcrypt.compare() permite verificar as senhas sem a necessidade de armazenar a senha original. Em quinto lugar, JWT fornece um mecanismo que permite ao servidor reconhecer um usuário autenticado. Em sexto lugar, JWT_SECRET permite assinar e verificar os tokens. Em sétimo lugar, a expiração do token após sete dias limita seu período de validade. Em oitavo lugar, o middleware autorize constitui uma barreira diante das rotas protegidas. Finalmente, os códigos HTTP como 400, 401 e 500 permitem gerenciar diferentes situações de erro. Todos esses elementos trabalham juntos para criar uma arquitetura de autenticação estruturada e mais segura do que uma aplicação que armazenasse senhas em texto puro ou deixasse todas as rotas acessíveis sem nenhum controle.

12. Gerenciamento dos erros de segurança

O sistema contempla várias situações de erro. Quando um usuário tenta criar uma conta com um endereço de e-mail que já está sendo utilizado, o servidor retorna o status 400 com a mensagem E-mail já utilizado. Quando um usuário tenta fazer login com um endereço que não existe, o servidor retorna Usuário não encontrado. Quando o endereço existe, mas a senha está incorreta, bcrypt.compare() retorna false e o servidor retorna Senha incorreta. Para as rotas protegidas, se nenhum JWT for enviado, o middleware retorna 401 com Token ausente. Se o JWT for inválido ou tiver expirado, jwt.verify() gera um erro que é capturado pelo bloco catch, e o servidor retorna 401 com Token inválido. Finalmente, erros inesperados provenientes do servidor ou do banco de dados podem ser capturados pelos blocos try/catch dos controladores e retornar um status 500. Esse gerenciamento permite que o frontend compreenda o resultado da requisição e exiba uma mensagem adequada ao usuário.

13. Explicação oral para a apresentação

Para apresentar esta parte diante de uma banca, pode-se explicar que o projeto possui um sistema de segurança baseado na autenticação JWT. Quando um usuário cria uma conta, o backend recebe seu nome, e-mail e senha por meio da rota /register. Antes de criar a conta, o Sequelize verifica no MySQL se o e-mail já existe. Em seguida, a senha é transformada em hash com bcrypt para que nunca seja armazenada em texto puro no banco de dados. Depois de criar o usuário, o servidor gera um token JWT assinado com uma chave secreta armazenada em JWT_SECRET. Durante o login, a rota /login procura o usuário por meio do seu e-mail e utiliza bcrypt.compare() para verificar a senha. Se as credenciais estiverem corretas, um JWT é gerado e enviado ao frontend. Para proteger uma rota, por exemplo /admin, utilizo um middleware chamado autorize. Esse middleware recupera o token do cabeçalho Authorization na forma de Bearer token e utiliza jwt.verify() para verificar sua validade. Se nenhum token for fornecido ou se o token for inválido ou tiver expirado, o servidor retorna um erro 401 e bloqueia o acesso. Se o token for válido, as informações do usuário são colocadas em req.user e next() permite que a requisição acesse a rota protegida. Essa arquitetura permite separar claramente o cadastro, o login, o hash das senhas, a geração do JWT e a proteção das rotas. Ela constitui a base da segurança do backend da minha aplicação.

14. Conclusão

O sistema desenvolvido permite implementar uma autenticação completa entre o frontend, o backend e o banco de dados MySQL. O Sequelize garante a comunicação com o MySQL e permite definir o modelo User. As rotas Express /register e /login permitem respectivamente criar uma conta e realizar a autenticação. O uso do bcrypt garante que as senhas não sejam armazenadas diretamente em sua forma original. O JWT permite então representar o estado de autenticação do usuário durante um período de tempo limitado. O middleware autorize verifica o token antes de permitir que uma requisição acesse uma rota protegida. Graças ao jwt.verify(), o servidor pode verificar o token e recuperar as informações do usuário em req.user. As rotas protegidas podem, assim, controlar o acesso às funcionalidades sensíveis. A arquitetura atual constitui uma base sólida de segurança backend com Node.js, Express, Sequelize, MySQL, bcrypt e JWT. Para uma segurança ainda mais completa em uma aplicação real de produção, essa base pode ser reforçada posteriormente com gerenciamento de funções e permissões, validação rigorosa dos dados, proteção contra ataques de força bruta, HTTPS, gerenciamento seguro do armazenamento dos tokens e um melhor gerenciamento das informações sensíveis.
