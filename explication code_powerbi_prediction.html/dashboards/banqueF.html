1 — Présentation générale du système Frontend

Dans cette partie du projet, nous avons développé la partie Frontend de l'application avec React et Redux Toolkit afin de gérer l'affichage du dashboard bancaire, de communiquer avec le Backend et de récupérer automatiquement le résultat d'une prédiction. Le Frontend joue le rôle d'interface entre l'utilisateur et le système de traitement des données. L'utilisateur accède à une page appelée Banque qui présente un dashboard Power BI ainsi qu'un résultat de prédiction généré par le Backend. Pour organiser correctement la communication entre les différents composants, nous avons utilisé Redux Toolkit. Redux permet de centraliser et de gérer l'état de l'application, tandis que createAsyncThunk permet de gérer une opération asynchrone, dans notre cas l'envoi d'une requête HTTP vers le Backend. Pour effectuer cette communication HTTP, nous utilisons Axios. Lorsque le composant React est chargé, la fonction useEffect() déclenche automatiquement l'action Redux createBanquePrediction en envoyant les valeurs x1: 10 et x2: 2. Redux lance alors une requête POST vers http://localhost:3000/banque. Le Backend reçoit ces données, réalise le traitement ou la prédiction et retourne une réponse. Cette réponse est ensuite enregistrée dans le store Redux grâce à l'état predictionData. Le composant React récupère ensuite les données grâce à useSelector() et actualise automatiquement l'interface. Le système gère également trois situations importantes : le chargement avec loading, la réussite avec fulfilled et l'erreur avec rejected. Lorsque la prédiction est disponible, le composant affiche sa valeur dans une carte de résultat et construit également un graphique avec Recharts afin de comparer les valeurs X1, X2 et la prédiction. En parallèle, un rapport Power BI est intégré dans la page avec une balise HTML iframe. Nous avons donc une architecture Frontend dans laquelle React s'occupe de l'interface utilisateur, Redux Toolkit gère l'état et les opérations asynchrones, Axios assure la communication avec le Backend, Power BI permet d'afficher le dashboard décisionnel et Recharts permet de représenter graphiquement le résultat de la prédiction.

2 — Redux Toolkit et gestion de l'état

Le premier fichier correspond au Slice Redux consacré à la prédiction bancaire. Redux Toolkit est utilisé pour simplifier la gestion de l'état global de l'application. La première ligne import { createSlice, createAsyncThunk } from "@reduxjs/toolkit"; permet d'importer deux fonctionnalités importantes. createSlice permet de créer une partie du store Redux appelée ici banque, tandis que createAsyncThunk permet de créer une action asynchrone destinée à communiquer avec le Backend. La ligne import axios from "axios"; importe Axios, une bibliothèque permettant d'effectuer des requêtes HTTP. Dans notre application, Axios est utilisé pour envoyer les données de prédiction au serveur. Le principe est donc de séparer la logique de communication avec le Backend de la logique d'affichage du composant React. Cela rend l'application plus organisée et plus facile à maintenir. 

import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";
import axios from "axios";

3 — Fonction createAsyncThunk

La fonction createBanquePrediction est créée avec createAsyncThunk. Son rôle est de réaliser une opération asynchrone permettant d'envoyer les données au Backend. Le premier argument "banque/create" représente le nom de l'action Redux. Le deuxième argument est une fonction asynchrone qui reçoit les données dans le paramètre data. La fonction utilise ensuite axios.post() pour envoyer une requête HTTP POST à l'adresse http://localhost:3000/banque. Le mot data représente les données envoyées par le composant React. Dans notre exemple, ces données sont x1: 10 et x2: 2. Le serveur reçoit donc ces deux valeurs et peut les utiliser pour effectuer la prédiction. Le mot-clé await permet d'attendre la réponse du serveur avant de continuer l'exécution. Une fois la réponse reçue, res.data permet de récupérer uniquement les données retournées par le Backend. La fonction retourne alors ces données avec return res.data. Redux Toolkit transmettra automatiquement cette réponse au reducer correspondant à l'état fulfilled. Si une erreur se produit pendant la requête Axios, l'instruction catch intercepte l'erreur. Nous utilisons alors rejectWithValue() pour transmettre l'erreur au reducer Redux. L'expression err.response?.data permet de récupérer le message envoyé par le serveur lorsqu'une réponse existe. Le symbole ?. correspond à l'accès optionnel et évite une erreur si response n'existe pas. Si aucune information d'erreur provenant du serveur n'est disponible, le message "Erreur serveur" est utilisé. Cette fonction constitue donc le pont entre le Frontend Redux et le Backend. 

export const createBanquePrediction = createAsyncThunk(
  "banque/create",
  async (data, { rejectWithValue }) => {
    try {
      const res = await axios.post(
        "http://localhost:3000/banque",
        data
      );

      return res.data;

    } catch (err) {

      return rejectWithValue(
        err.response?.data || "Erreur serveur"
      );

    }
  }
);

4 — Création du banqueSlice et état initial

Après la création de l'action asynchrone, nous créons le banqueSlice avec createSlice(). Ce Slice représente la partie du store Redux consacrée à la fonctionnalité bancaire. La propriété name: "banque" donne un nom à cette partie de l'état. La propriété initialState définit l'état initial de cette fonctionnalité. Nous avons trois informations principales. La première est predictionData: null, ce qui signifie qu'au démarrage aucune prédiction n'est encore disponible. La deuxième est loading: false, qui indique qu'aucune requête n'est actuellement en cours au moment initial. La troisième est error: null, qui indique qu'aucune erreur n'a encore été rencontrée. Cette organisation permet au composant React de savoir précisément dans quelle situation se trouve la requête : attente, chargement, succès ou erreur. 

const banqueSlice = createSlice({
  name: "banque",

  initialState: {
    predictionData: null,
    loading: false,
    error: null,
  },

  reducers: {},

  extraReducers: (builder) => {
    ...
  },
});

5 — Gestion de l'état pending

Lorsque createBanquePrediction est exécuté et que la requête vers le Backend commence, Redux Toolkit déclenche automatiquement l'état pending. Le code .addCase(createBanquePrediction.pending, (state) => { ... }) permet de définir ce qui doit arriver pendant le chargement. Nous mettons alors state.loading = true. Le composant React pourra ainsi savoir qu'une requête est en cours et afficher le message Loading prediction.... Nous réinitialisons également state.error = null afin de supprimer une éventuelle erreur précédente. Cette gestion permet d'avoir une interface dynamique et d'informer l'utilisateur que le système est actuellement en train de récupérer la prédiction. 

.addCase(createBanquePrediction.pending, (state) => {
  state.loading = true;
  state.error = null;
})

6 — Gestion de l'état fulfilled

Lorsque la requête Axios est terminée avec succès et que le Backend retourne une réponse correcte, Redux Toolkit déclenche l'état fulfilled. Le code .addCase(createBanquePrediction.fulfilled, (state, action) => { ... }) récupère alors la réponse du serveur dans action.payload. Nous mettons state.loading = false car la requête est terminée. Ensuite, state.predictionData = action.payload permet d'enregistrer le résultat de la prédiction dans le store Redux. Cette donnée devient alors disponible pour les composants React qui utilisent useSelector(). Le fonctionnement est donc très important : le Backend produit le résultat, Redux le stocke dans son état global et React récupère automatiquement cette nouvelle valeur afin de mettre à jour l'affichage. 

.addCase(createBanquePrediction.fulfilled, (state, action) => {
  state.loading = false;
  state.predictionData = action.payload;
})

7 — Gestion de l'état rejected

Si la requête échoue, par exemple si le Backend est arrêté, si l'URL est incorrecte ou si le serveur retourne une erreur, Redux Toolkit déclenche l'état rejected. Le code .addCase(createBanquePrediction.rejected, (state, action) => { ... }) permet de gérer cette situation. Nous mettons state.loading = false car la requête est terminée même si elle a échoué. Ensuite, state.error = action.payload récupère le message d'erreur transmis par rejectWithValue(). Le composant React peut alors lire cet état et afficher un message d'erreur à l'utilisateur. Cette organisation évite de laisser l'utilisateur sans information lorsqu'une communication avec le serveur échoue. 

.addCase(createBanquePrediction.rejected, (state, action) => {
  state.loading = false;
  state.error = action.payload;
})

8 — Cycle complet Redux

Le fonctionnement complet de Redux Toolkit peut être résumé ainsi : le composant React déclenche dispatch(createBanquePrediction(...)). Redux Toolkit lance alors l'action asynchrone. Dès le début de la requête, l'état pending est déclenché et loading devient true. Axios envoie ensuite les données au Backend. Si le Backend retourne correctement la prédiction, l'état fulfilled est déclenché et le résultat est enregistré dans predictionData. Si la requête échoue, l'état rejected est déclenché et l'erreur est enregistrée dans error. React observe les changements du store grâce à useSelector() et met automatiquement l'interface à jour. Cette architecture permet donc de gérer proprement les opérations asynchrones sans placer toute la logique directement dans le composant React.

Flux de données :

React → dispatch() → Redux Toolkit → createAsyncThunk → Axios → Backend → Prédiction → Redux Store → useSelector() → Interface React

9 — Composant React Banque

Le deuxième fichier correspond au composant React appelé Banque. Son rôle est de construire l'interface utilisateur du dashboard bancaire et de récupérer les données de prédiction stockées dans Redux. La première ligne import React, { useEffect } from "react"; importe React ainsi que le Hook useEffect. Ensuite, useDispatch et useSelector sont importés depuis react-redux. useDispatch() permet au composant d'envoyer une action Redux, tandis que useSelector() permet de lire une information provenant du store Redux. Le fichier CSS Banque.css est également importé afin de gérer le style de la page. Enfin, plusieurs composants de Recharts sont importés afin de construire le graphique : BarChart, Bar, XAxis, YAxis, Tooltip, CartesianGrid, ResponsiveContainer et Legend. 

import React, { useEffect } from "react";
import { useDispatch, useSelector } from "react-redux";
import { createBanquePrediction } from "../redux/banqueSlice";
import "./Banque.css";

10 — useDispatch

Dans le composant Banque, nous utilisons const dispatch = useDispatch(). Le Hook useDispatch() permet d'obtenir la fonction dispatch qui sert à envoyer des actions vers Redux. Grâce à cette fonction, le composant React peut demander à Redux d'exécuter la prédiction bancaire. Sans dispatch, le composant ne pourrait pas déclencher directement notre action createBanquePrediction. Le rôle de dispatch est donc de faire circuler une action depuis le composant React vers le système Redux. 

const dispatch = useDispatch();

11 — useSelector et récupération de l'état Redux

Le Hook useSelector() permet au composant React de récupérer les données présentes dans le store Redux. Dans notre code, nous récupérons trois informations. La première est predictionData, qui contient le résultat retourné par le Backend. La deuxième est loading, qui indique si la requête est en cours. La troisième est error, qui contient éventuellement un message d'erreur. L'expression state.banque?.predictionData signifie que nous cherchons la propriété predictionData dans la partie banque du store. Le symbole ?. permet d'éviter une erreur si l'objet banque n'existe momentanément pas. Grâce à useSelector(), lorsque Redux modifie ces informations, React détecte le changement et actualise automatiquement le composant. 

const predictionData = useSelector(
  (state) => state.banque?.predictionData
);

const loading = useSelector(
  (state) => state.banque?.loading
);

const error = useSelector(
  (state) => state.banque?.error
);

12 — useEffect et lancement automatique de la prédiction

Le Hook useEffect() est utilisé pour exécuter automatiquement une opération lorsque le composant est chargé. Dans notre code, nous utilisons dispatch(createBanquePrediction({ x1: 10, x2: 2 })). Cela signifie que lorsque la page Banque est affichée, le composant envoie automatiquement une action Redux afin de demander une prédiction au Backend. Les valeurs envoyées sont x1: 10 et x2: 2. Le tableau de dépendances contient dispatch. Dans ce contexte, l'effet est exécuté lors du montage du composant. Cette approche permet donc de lancer automatiquement la prédiction sans demander à l'utilisateur de cliquer sur un bouton. Le parcours est alors : affichage du composant, exécution de useEffect(), appel de dispatch(), lancement de createBanquePrediction, requête Axios vers le Backend, réception de la réponse et mise à jour de Redux. 

useEffect(() => {
  dispatch(
    createBanquePrediction({
      x1: 10,
      x2: 2,
    })
  );
}, [dispatch]);

13 — Préparation des données du graphique

Après avoir récupéré le résultat dans Redux, le composant construit une nouvelle variable appelée chartData. Cette variable est destinée à Recharts. L'expression conditionnelle predictionData ? [...] : [] signifie que si une prédiction existe, nous créons un tableau contenant les données du graphique. Sinon, nous créons un tableau vide. L'objet contient une propriété name avec la valeur "Banque", puis les valeurs X1, X2 et Prediction. Pour X1, nous utilisons predictionData.x1 || 0. Cela signifie que si la valeur X1 existe, elle est utilisée ; sinon la valeur 0 est utilisée. Le même principe est appliqué à X2 et à la prédiction. Cette étape transforme donc les données reçues du Backend dans une structure directement exploitable par le graphique Recharts. 

const chartData = predictionData
  ? [
      {
        name: "Banque",
        X1: predictionData.x1 || 0,
        X2: predictionData.x2 || 0,
        Prediction:
          predictionData.prediction || 0,
      },
    ]
  : [];

14 — Intégration du dashboard Power BI

Le composant React intègre également un rapport Power BI grâce à une balise HTML iframe. L'objectif est d'afficher directement dans notre application Web un dashboard décisionnel créé avec Power BI. La classe powerbi-frame permet d'appliquer le style défini dans Banque.css. La propriété title="BANQUE" donne un titre à l'élément intégré. La propriété src contient l'adresse du rapport Power BI publié. La propriété frameBorder="0" permet de supprimer la bordure de l'iframe et allowFullScreen autorise l'affichage en plein écran. Cette intégration permet donc de réunir dans une même page deux dimensions du projet : d'une part le dashboard décisionnel Power BI et d'autre part la prédiction générée dynamiquement par le Backend et affichée par React. 

<div className="powerbi-container">

  <iframe
    className="powerbi-frame"

  />

15 — Affichage du chargement

Le composant utilise la variable loading provenant de Redux pour informer l'utilisateur lorsqu'une prédiction est en cours. La condition {loading && (...)} signifie que le paragraphe sera affiché uniquement lorsque loading vaut true. Le message affiché est Loading prediction.... Cela correspond à l'état pending défini dans le Slice Redux. Il existe donc une relation directe entre le Backend, Redux et l'interface : lorsque la requête démarre, Redux active loading et React affiche le message de chargement. 

{loading && (
  <p className="loading">
    Loading prediction...
  </p>
)}

16 — Affichage des erreurs

Le composant prévoit également la possibilité qu'une erreur se produise. La condition {error && (...)} signifie que le message d'erreur est affiché uniquement lorsqu'une erreur existe dans le store Redux. Cette erreur peut provenir d'Axios, du Backend ou d'un problème de communication avec le serveur. La valeur de error a été enregistrée dans Redux lorsque l'état rejected a été déclenché. React récupère donc cette valeur grâce à useSelector() et l'affiche à l'utilisateur dans un paragraphe ayant la classe CSS error. 

{error && (
  <p className="error">
    {error}
  </p>
)}

17 — État d'attente

Le composant prévoit également une situation dans laquelle aucune prédiction n'est disponible et aucune requête n'est actuellement en cours. La condition !loading && !error && !predictionData vérifie les trois éléments : le chargement est terminé, aucune erreur n'existe et aucune donnée de prédiction n'est encore disponible. Dans cette situation, l'application affiche le message Waiting for prediction result.... Cela permet de gérer proprement l'état initial de la page avant que le résultat de la prédiction soit reçu. 

{!loading &&
  !error &&
  !predictionData && (
    <p className="waiting">
      ⏳ Waiting for prediction result...
    </p>
)}

18 — Affichage du résultat de la prédiction

Lorsque predictionData existe, le composant affiche une carte contenant le résultat de la prédiction. La condition {predictionData && (...)} permet de rendre cette partie de l'interface uniquement lorsque les données sont disponibles. Le titre 📌 Résultat indique clairement à l'utilisateur qu'il s'agit du résultat produit par le modèle. La valeur affichée utilise predictionData.prediction?.toFixed(2). La propriété prediction correspond au résultat envoyé par le Backend. La fonction toFixed(2) permet d'afficher le nombre avec deux chiffres après la virgule. Le symbole ?. permet de vérifier que la propriété existe avant d'appeler la méthode. Cette carte constitue donc la partie principale de l'affichage du résultat prédictif. 

{predictionData && (
  <div className="prediction-card">

    <h2 className="prediction-title">
      📌 Résultat
    </h2>

    <div className="prediction-value">
      {predictionData.prediction?.toFixed(2)}
    </div>

  </div>
)}

19 — Création du graphique avec Recharts

Après l'affichage de la valeur numérique, le composant crée un graphique avec la bibliothèque Recharts. L'objectif est de présenter visuellement les valeurs X1, X2 et Prediction. Le composant ResponsiveContainer permet au graphique de s'adapter automatiquement à la largeur disponible. La propriété width="100%" indique que le graphique utilise toute la largeur de son conteneur et height={350} définit une hauteur de 350 pixels. Le composant BarChart reçoit les données avec data={chartData}. Le composant CartesianGrid affiche une grille facilitant la lecture du graphique. XAxis définit l'axe horizontal et utilise dataKey="name" afin d'afficher le nom de la catégorie, ici Banque. YAxis représente l'axe vertical contenant les valeurs numériques. Tooltip affiche des informations lorsque l'utilisateur positionne la souris sur une barre. Legend affiche la légende des différentes séries. Enfin, trois composants Bar représentent respectivement X1, X2 et Prediction. Chaque barre utilise une clé de données différente grâce à dataKey. Le graphique permet donc d'avoir une représentation visuelle et comparative des données utilisées pour la prédiction et du résultat obtenu.

20 — Architecture complète du Frontend

Les deux fichiers Redux et React fonctionnent ensemble selon une architecture organisée. Le composant Banque constitue la partie visuelle. Lorsqu'il est chargé, useEffect() appelle dispatch() avec l'action createBanquePrediction. Cette action est définie dans banqueSlice.js avec createAsyncThunk. Redux Toolkit démarre alors une requête Axios vers le Backend avec les valeurs X1 et X2. Pendant cette communication, Redux passe à l'état pending et la variable loading devient vraie. Lorsque le Backend retourne une réponse correcte, Redux passe à l'état fulfilled et place la réponse dans predictionData. Le composant React récupère cette donnée grâce à useSelector(). React détecte automatiquement la modification de l'état et actualise l'interface. Le résultat est alors affiché dans la carte de prédiction et les données sont préparées dans chartData pour construire le graphique Recharts. Si une erreur apparaît pendant la communication, Redux passe à l'état rejected, enregistre l'erreur dans error et React affiche le message correspondant. Parallèlement, l'iframe Power BI affiche le dashboard décisionnel. Nous avons donc une séparation claire entre la présentation, la gestion de l'état, la communication avec le serveur et la visualisation des données.

21 — Rôle de Redux et rôle de React

Dans cette architecture, React et Redux ont des responsabilités différentes mais complémentaires. React est principalement responsable de l'interface utilisateur : il construit la page, affiche le dashboard Power BI, affiche le résultat de la prédiction et construit le graphique. Redux Toolkit est responsable de la gestion de l'état et de la communication avec le Backend. Le Slice Redux contient les informations predictionData, loading et error. createAsyncThunk gère l'opération asynchrone et Axios communique avec le serveur. React utilise ensuite useSelector() pour lire l'état Redux et useDispatch() pour envoyer des actions. Cette séparation rend le code plus propre car la logique de récupération des données n'est pas entièrement mélangée avec le code d'affichage. React s'occupe donc principalement de présenter les informations alors que Redux organise leur circulation et leur état dans l'application.

22 — Gestion des trois états de la requête

Un élément important de cette architecture est la gestion des trois états générés automatiquement par createAsyncThunk. Le premier état est pending : il correspond au moment où la requête est en cours et permet d'afficher un indicateur de chargement. Le deuxième état est fulfilled : il correspond à une requête réussie et permet d'enregistrer la réponse dans predictionData. Le troisième état est rejected : il correspond à une requête échouée et permet d'enregistrer le problème dans error. Grâce à ces trois états, l'interface React peut réagir automatiquement à l'évolution de la communication avec le Backend. L'utilisateur sait donc si le système est en train de travailler, si la prédiction est disponible ou si une erreur s'est produite.

pending → Requête en cours → loading = true

fulfilled → Requête réussie → predictionData = résultat

rejected → Requête échouée → error = message

23 — Conclusion

Pour conclure, ces deux fichiers constituent une partie essentielle du Frontend de notre application de prédiction bancaire. Le fichier Redux utilise Redux Toolkit afin de centraliser l'état de la fonctionnalité bancaire et de gérer la communication asynchrone avec le Backend grâce à createAsyncThunk et Axios. L'état initial contient les informations nécessaires pour connaître le résultat de la prédiction, l'état du chargement et les éventuelles erreurs. Les trois états pending, fulfilled et rejected permettent de gérer automatiquement les différentes étapes de la requête. Le composant React Banque utilise ensuite useDispatch() pour déclencher l'action Redux et useSelector() pour récupérer les informations du store. Le Hook useEffect() permet de lancer automatiquement la prédiction lorsque le composant est chargé. Une fois le résultat reçu, React affiche la valeur de la prédiction dans une carte et utilise Recharts pour créer une représentation graphique comparant X1, X2 et la prédiction. Le composant intègre également un dashboard Power BI grâce à une iframe afin de réunir l'analyse décisionnelle et l'analyse prédictive dans une même interface. L'architecture finale repose donc sur une communication entre React, Redux Toolkit, Axios, le Backend, le modèle de prédiction, Power BI et Recharts. Cette organisation permet de construire une application Frontend dynamique, structurée et capable de présenter à l'utilisateur aussi bien les données décisionnelles que les résultats prédictifs.

24 — Explication orale pour la présentation

Pour présenter cette partie devant un jury, on peut expliquer que le Frontend de l'application est développé avec React et que Redux Toolkit est utilisé pour gérer l'état et la communication avec le Backend. Dans le fichier Redux, j'ai créé une action asynchrone avec createAsyncThunk. Cette action utilise Axios pour envoyer les valeurs X1 et X2 au Backend à travers une requête POST. Redux Toolkit gère automatiquement trois états : pending lorsque la requête est en cours, fulfilled lorsque la réponse est reçue correctement et rejected lorsqu'une erreur se produit. Le résultat retourné par le Backend est enregistré dans predictionData. Dans le composant React Banque, j'utilise useDispatch pour déclencher l'action et useSelector pour récupérer les données depuis Redux. Avec useEffect, la prédiction est lancée automatiquement lorsque la page est chargée. Lorsque la réponse arrive, React affiche le résultat dans une carte et utilise Recharts pour représenter graphiquement X1, X2 et la prédiction. J'ai également intégré un dashboard Power BI avec une iframe afin d'afficher les résultats décisionnels dans la même interface.
