1. Présentation générale de la sécurité

Dans cette partie du projet, un système complet d'authentification et de sécurisation des routes a été mis en place afin de protéger l'accès aux fonctionnalités sensibles de l'application. Le système repose principalement sur plusieurs technologies complémentaires : Node.js pour l'exécution du backend, Express pour la création des routes HTTP, Sequelize comme ORM permettant de communiquer avec MySQL, bcryptjs pour protéger les mots de passe et JSON Web Token, appelé JWT, pour gérer l'authentification des utilisateurs. Le principe général est de permettre à un utilisateur de créer un compte avec un nom, une adresse email et un mot de passe, puis de pouvoir se connecter avec ces informations. Lors de l'inscription, le mot de passe original n'est jamais enregistré directement dans la base de données. Il est transformé en une valeur hachée grâce à bcrypt. Lors de la connexion, le mot de passe fourni par l'utilisateur est comparé au hash enregistré dans MySQL. Si les informations sont correctes, le serveur génère un token JWT contenant certaines informations permettant d'identifier l'utilisateur. Le frontend reçoit ensuite ce token et doit le transmettre lors de l'accès aux routes protégées. Le middleware autorize récupère alors le token dans l'en-tête HTTP Authorization, vérifie sa validité avec jwt.verify() et la clé secrète JWT_SECRET. Lorsque le token est valide, les informations décodées sont placées dans req.user et la fonction next() permet à la requête de continuer. Si aucun token n'est fourni ou si le token est invalide ou expiré, le serveur bloque l'accès et retourne une réponse HTTP 401 Unauthorized. L'architecture permet donc de séparer clairement plusieurs niveaux de sécurité : la gestion des utilisateurs dans MySQL, la protection des mots de passe avec bcrypt, l'authentification avec JWT et la protection des routes avec un middleware Express.

2. Connexion à MySQL avec Sequelize

Le premier niveau du système correspond à la connexion entre le serveur Node.js et la base de données MySQL. Pour réaliser cette connexion, le projet utilise Sequelize. Sequelize est un ORM permettant de manipuler une base de données relationnelle à travers des modèles JavaScript. Cela signifie que le développeur peut utiliser des méthodes comme findOne() ou create() au lieu d'écrire directement toutes les requêtes SQL. Dans le fichier config/db.js, la bibliothèque Sequelize est importée avec const { Sequelize, DataTypes } = require("sequelize"). L'objet sequelize est ensuite créé avec le nom de la base de données POWERBI_PREDICTION, l'utilisateur MySQL root, un mot de passe vide dans cet environnement de développement, l'hôte localhost et le dialecte mysql. Le paramètre localhost indique que MySQL fonctionne sur la même machine que le serveur Node.js, tandis que dialect: "mysql" indique à Sequelize que le système de gestion de base de données utilisé est MySQL. Enfin, la connexion est exportée avec module.exports afin qu'elle puisse être utilisée par les modèles et les contrôleurs de l'application. Cette organisation permet de centraliser la configuration de la base de données et de réutiliser la même connexion dans les différentes parties du backend. 

const { Sequelize, DataTypes } = require("sequelize");

const sequelize = new Sequelize(
    "POWERBI_PREDICTION",
    "root",
    "",
    {
        host: "localhost",
        dialect: "mysql"
    }
);

module.exports = {
    sequelize,
};

3. Création du modèle User

Le modèle User représente la structure des utilisateurs enregistrés dans la base de données. Le fichier commence par importer DataTypes depuis Sequelize ainsi que la connexion sequelize définie dans config/db.js. La fonction sequelize.define("User", ...) permet ensuite de créer un modèle appelé User. Ce modèle contient quatre informations principales : l'identifiant, le nom, l'email et le mot de passe. Le champ id est de type entier grâce à DataTypes.INTEGER, il est automatiquement incrémenté avec autoIncrement: true et constitue la clé primaire avec primaryKey: true. Le champ name est une chaîne de caractères et allowNull: false indique que le nom est obligatoire. Le champ email est également une chaîne de caractères, il est obligatoire et possède la propriété unique: true. Cette dernière permet d'empêcher que plusieurs comptes utilisent la même adresse email. Enfin, le champ password est obligatoire et est utilisé pour enregistrer le mot de passe sous sa forme hachée. Il est très important de préciser que la valeur enregistrée dans cette colonne ne doit pas être le mot de passe original. Le contrôleur utilise bcrypt avant l'enregistrement afin de transformer le mot de passe en hash. 

const { DataTypes } = require("sequelize");
const { sequelize } = require("../config/db");

const User = sequelize.define("User", {

    id: {
        type: DataTypes.INTEGER,
        autoIncrement: true,
        primaryKey: true,
    },

    name: {
        type: DataTypes.STRING,
        allowNull: false,
    },

    email: {
        type: DataTypes.STRING,
        allowNull: false,
        unique: true,
    },

    password: {
        type: DataTypes.STRING,
        allowNull: false,
    },

});

module.exports = User;

4. Fonction Register : inscription d'un utilisateur

La fonction register est responsable de l'inscription d'un nouvel utilisateur. Elle est déclarée avec async car elle réalise plusieurs opérations asynchrones, notamment les recherches dans la base de données, le hachage du mot de passe et la création de l'utilisateur. Les informations name, email et password sont récupérées depuis req.body, ce qui signifie qu'elles sont envoyées par le frontend dans le corps de la requête HTTP. Avant de créer le compte, le serveur utilise User.findOne() avec where: { email } afin de rechercher si un utilisateur possède déjà cette adresse email. Si un utilisateur existe, l'inscription est immédiatement arrêtée et le serveur retourne une réponse HTTP 400 avec le message Email déjà utilisé. Cette vérification est importante car elle empêche la création de plusieurs comptes avec la même adresse email. Si aucun compte n'existe, le serveur utilise ensuite bcrypt.hash(password, 10). Cette opération transforme le mot de passe original en une valeur hachée. Le nombre 10 représente le coût de calcul utilisé par bcrypt pour générer le hash. Le mot de passe original n'est donc pas directement enregistré dans MySQL. Après cette étape, User.create() crée l'utilisateur avec son nom, son email et le mot de passe haché. Une fois l'utilisateur créé, le serveur génère un token JWT grâce à jwt.sign(). Le payload du token contient notamment l'identifiant et l'email de l'utilisateur. Le token est signé avec la clé secrète située dans process.env.JWT_SECRET et sa durée de validité est fixée à sept jours avec expiresIn: "7d". Enfin, le serveur retourne une réponse HTTP 201 contenant l'utilisateur et le token. Le frontend peut alors utiliser ce token pour les futures requêtes nécessitant une authentification. 

exports.register = async (req, res) => {
    try {

        const { name, email, password } = req.body;

        const exist = await User.findOne({
            where: { email }
        });

        if (exist) {
            return res.status(400).json(
                "Email déjà utilisé"
            );
        }

        const hashedPassword =
            await bcrypt.hash(password, 10);

        const user = await User.create({
            name,
            email,
            password: hashedPassword,
        });

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.status(201).json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

5. Fonction Login : connexion de l'utilisateur

La fonction login permet à un utilisateur déjà enregistré de se connecter à l'application. Le serveur récupère l'email et le mot de passe depuis req.body, puis utilise User.findOne() pour rechercher l'utilisateur correspondant à cette adresse email dans MySQL. Si aucun utilisateur n'est trouvé, le serveur retourne une réponse HTTP 400 avec le message Utilisateur introuvable. Si l'utilisateur existe, le serveur ne compare pas directement deux mots de passe en clair. Il utilise bcrypt.compare(password, user.password) afin de comparer le mot de passe saisi avec le hash enregistré dans la base de données. Si la comparaison retourne false, le serveur refuse la connexion avec le message Mot de passe incorrect. Si le mot de passe est correct, le serveur génère un nouveau token JWT avec jwt.sign(). Comme lors de l'inscription, le token contient l'identifiant et l'email de l'utilisateur, il est signé avec JWT_SECRET et possède une durée de validité de sept jours. Le serveur retourne ensuite un objet JSON contenant l'utilisateur et son token. Le frontend peut conserver ce token et l'envoyer lors de l'accès aux fonctionnalités protégées. Cette étape constitue donc le mécanisme d'authentification de l'application : l'utilisateur prouve son identité grâce à son email et son mot de passe, puis reçoit un token permettant au serveur de reconnaître cette authentification lors des requêtes suivantes. 

exports.login = async (req, res) => {
    try {

        const { email, password } = req.body;

        const user = await User.findOne({
            where: { email },
        });

        if (!user) {
            return res.status(400).json(
                "Utilisateur introuvable"
            );
        }

        const validPassword =
            await bcrypt.compare(
                password,
                user.password
            );

        if (!validPassword) {
            return res.status(400).json(
                "Mot de passe incorrect"
            );
        }

        const token = jwt.sign(
            {
                id: user.id,
                email: user.email,
            },
            process.env.JWT_SECRET,
            {
                expiresIn: "7d"
            }
        );

        res.json({
            user,
            token,
        });

    } catch (err) {

        res.status(500).json(err.message);

    }
};

6. Authentification avec JSON Web Token

JSON Web Token, généralement appelé JWT, est utilisé dans ce projet pour gérer l'authentification entre le frontend et le backend. Après une inscription ou une connexion réussie, le serveur génère un token grâce à jwt.sign(). Ce token contient un payload avec des informations permettant d'identifier l'utilisateur, notamment son id et son email. Le token est signé avec process.env.JWT_SECRET. Cette clé secrète est importante car elle permet au serveur de vérifier que le token présenté par le client correspond bien à un token signé par le serveur. La clé doit être conservée dans une variable d'environnement et ne doit pas être publiée directement dans le code source. Le token possède également une durée de validité de sept jours grâce à expiresIn: "7d". Cela signifie qu'un token expiré ne doit plus permettre l'accès aux routes protégées. Le JWT permet donc d'éviter de transmettre le mot de passe à chaque requête. Une fois connecté, le frontend utilise le token comme preuve d'authentification et l'envoie au backend lorsqu'il souhaite accéder à une route protégée.

Principe important :

Le JWT ne remplace pas le mot de passe et ne doit pas être considéré comme le mot de passe. Il représente une preuve temporaire d'authentification créée par le serveur.

7. Middleware autorize : protection des routes

Le fichier autorize.js contient un middleware Express dont le rôle est de contrôler l'accès aux routes protégées. Le middleware importe d'abord la bibliothèque jsonwebtoken. La fonction autorize reçoit trois paramètres : req, qui représente la requête HTTP, res, qui permet d'envoyer la réponse au client, et next, qui permet de continuer vers la prochaine fonction lorsque l'utilisateur est autorisé. Le middleware récupère ensuite le token depuis req.headers.authorization. Le frontend doit envoyer l'en-tête sous la forme Authorization: Bearer TOKEN. La méthode split(" ") sépare le mot Bearer du token et l'index [1] récupère uniquement le token. L'opérateur ?. permet d'éviter une erreur si l'en-tête n'existe pas. Le middleware vérifie ensuite si le token est présent. Si aucun token n'est trouvé, l'accès est immédiatement refusé avec le statut HTTP 401 et le message Token manquant. Si le token existe, le serveur utilise jwt.verify() avec le token et process.env.JWT_SECRET. Cette opération permet de vérifier que le token est valide et qu'il n'est pas expiré. Si la vérification réussit, les informations décodées sont placées dans req.user. Cette étape est très utile car les fonctions suivantes peuvent maintenant connaître l'utilisateur authentifié. Enfin, next() permet à la requête de continuer vers la route protégée. Si la vérification échoue, par exemple parce que le token est invalide ou expiré, l'exécution passe dans le bloc catch et le serveur retourne une réponse HTTP 401 avec le message Token invalide. Ainsi, le middleware constitue une véritable barrière de sécurité devant les routes sensibles. 

const jwt = require("jsonwebtoken");

const autorize = (req, res, next) => {

    const token =
        req.headers.authorization?.split(" ")[1];

    if (!token) {

        return res.status(401).json({
            message: "Token manquant",
        });

    }

    try {

        const decoded = jwt.verify(
            token,
            process.env.JWT_SECRET
        );

        req.user = decoded;

        next();

    } catch (error) {

        return res.status(401).json({
            message: "Token invalide",
        });

    }
};

module.exports = autorize;

8. Routes d'inscription et de connexion

Le fichier des routes utilisateur permet de connecter les fonctions du contrôleur aux endpoints HTTP de l'application. Express fournit la fonction Router() permettant de créer un ensemble de routes indépendantes. Le fichier importe ensuite les fonctions register et login depuis le contrôleur utilisateur. La première route est router.post("/register", register). Elle indique que lorsqu'une requête HTTP de type POST est envoyée vers /register, Express exécute la fonction register. Cette fonction reçoit les données du formulaire, vérifie l'email, hache le mot de passe, crée l'utilisateur et génère le JWT. La deuxième route est router.post("/login", login). Lorsqu'une requête POST est envoyée vers /login, Express exécute la fonction login. Cette fonction vérifie l'utilisateur, compare le mot de passe avec bcrypt et génère un nouveau token JWT si les informations sont correctes. Enfin, module.exports = router permet d'exporter le routeur afin qu'il puisse être utilisé dans le fichier principal du serveur. Cette séparation entre les routes et les contrôleurs permet d'organiser correctement le backend : les routes définissent les URLs et les méthodes HTTP, tandis que les contrôleurs contiennent la logique métier. 

const express = require("express");

const router = express.Router();

const { sequelize } = require("../config/db");

const {
    register,
    login,
} = require("../Controllers/userController");

router.post("/register", register);

router.post("/login", login);

module.exports = router;

9. Route Admin protégée par JWT

Une route spéciale permet également de démontrer concrètement l'utilisation du middleware de sécurité. Le routeur Express définit la route GET /admin et place le middleware autorize entre l'URL et le contrôleur. L'ordre est très important : lorsqu'une requête arrive sur cette route, Express exécute d'abord autorize. Le middleware récupère le token JWT depuis l'en-tête Authorization, vérifie sa validité avec jwt.verify(), place les informations de l'utilisateur dans req.user, puis appelle next(). Ce n'est qu'après cette vérification que la fonction de la route est exécutée. Si le token est absent, le contrôleur de la route n'est jamais exécuté et le serveur retourne une erreur 401. Si le token est invalide ou expiré, le même principe s'applique. Lorsque le token est valide, la route peut retourner le message Bienvenue Admin ainsi que l'utilisateur contenu dans req.user. Cette route montre donc comment le middleware devient une barrière entre le client et une fonctionnalité protégée. Il faut toutefois distinguer l'authentification de l'autorisation : le middleware présenté vérifie que le token est valide et identifie l'utilisateur, mais le code fourni ne vérifie pas encore que l'utilisateur possède réellement un rôle administrateur. Pour avoir une véritable autorisation basée sur les rôles, il faudrait également stocker un rôle, par exemple admin ou user, dans le modèle utilisateur et vérifier ce rôle avant d'autoriser l'accès à une route strictement réservée aux administrateurs. 

const express = require("express");
const router = express.Router();

const autorize =
    require("../middleware/autorize");

/* =========================
   ADMIN ROUTE
========================= */

router.get(
    "/admin",
    autorize,
    (req, res) => {

        res.json({
            message: "Bienvenue Admin",
            user: req.user,
        });

    }
);

module.exports = router;
⚠️ Point important :

Dans le code actuel, le middleware vérifie que l'utilisateur possède un JWT valide, mais il ne vérifie pas encore que cet utilisateur possède réellement le rôle admin. Le nom de la route /admin indique une route destinée à l'administration, mais la sécurité actuelle correspond principalement à une authentification. Une vérification de rôle supplémentaire serait nécessaire pour mettre en place une véritable autorisation administrateur.

10. Fonctionnement complet du système

Le fonctionnement global de la sécurité commence lorsque l'utilisateur utilise le frontend pour créer un compte. Le frontend envoie une requête POST vers la route /register avec le nom, l'email et le mot de passe. Express reçoit cette requête et appelle le contrôleur register. Le contrôleur vérifie dans MySQL, via Sequelize, si l'email existe déjà. Si l'adresse est disponible, bcrypt transforme le mot de passe en hash puis Sequelize crée le nouvel utilisateur dans la base de données. Le serveur génère ensuite un JWT signé avec JWT_SECRET et valide pendant sept jours. Lors d'une connexion, le frontend utilise la route /login. Le contrôleur recherche l'utilisateur par son email puis utilise bcrypt.compare() pour vérifier le mot de passe. Si les informations sont correctes, un JWT est généré et envoyé au frontend. Pour accéder ensuite à une route protégée comme /admin, le frontend doit envoyer le token dans l'en-tête Authorization avec le format Bearer TOKEN. Express exécute alors le middleware autorize. Celui-ci récupère le token, utilise jwt.verify() pour contrôler sa validité et place les informations de l'utilisateur dans req.user. Si la vérification réussit, next() autorise la requête à poursuivre son exécution. Si le token est absent, invalide ou expiré, l'accès est refusé avec une erreur HTTP 401. Cette architecture crée donc une chaîne de sécurité complète allant du frontend vers Express, puis vers le middleware JWT, le contrôleur, Sequelize et enfin MySQL.

Frontend ↓ POST /register ↓ Express Router ↓ register() ↓ Vérification de l'email ↓ bcrypt.hash() ↓ MySQL / Sequelize ↓ Création User ↓ jwt.sign() ↓ JWT ↓ Frontend ↓ Authorization: Bearer TOKEN ↓ GET /admin ↓ autorize() ↓ jwt.verify() ↓ ┌──────────────────────────┐ │ Token valide ? │ └──────────────────────────┘ ↓ ↓ NON OUI ↓ ↓ 401 req.user ↓ next() ↓ /admin ↓ Réponse

11. Les différentes couches de sécurité

La sécurité de l'application repose sur plusieurs mécanismes complémentaires et non sur une seule technologie. Premièrement, Sequelize permet de structurer les données utilisateurs et de communiquer avec MySQL. Deuxièmement, le modèle User impose certaines contraintes comme l'obligation du nom, de l'email et du mot de passe ainsi que l'unicité de l'adresse email. Troisièmement, bcrypt protège les mots de passe grâce au hachage avant leur enregistrement. Quatrièmement, bcrypt.compare() permet de vérifier les mots de passe sans avoir besoin de stocker le mot de passe original. Cinquièmement, JWT fournit un mécanisme permettant au serveur de reconnaître un utilisateur authentifié. Sixièmement, JWT_SECRET permet de signer et de vérifier les tokens. Septièmement, l'expiration du token après sept jours limite sa durée de validité. Huitièmement, le middleware autorize constitue une barrière devant les routes protégées. Enfin, les codes HTTP comme 400, 401 et 500 permettent de gérer différentes situations d'erreur. Tous ces éléments travaillent ensemble afin de créer une architecture d'authentification structurée et plus sûre qu'une application qui stockerait les mots de passe en clair ou qui laisserait toutes les routes accessibles sans contrôle.

12. Gestion des erreurs de sécurité

Le système prévoit plusieurs situations d'erreur. Lorsqu'un utilisateur tente de créer un compte avec une adresse email déjà utilisée, le serveur retourne le statut 400 avec le message Email déjà utilisé. Lorsqu'un utilisateur tente de se connecter avec une adresse qui n'existe pas, le serveur retourne Utilisateur introuvable. Lorsque l'adresse existe mais que le mot de passe est incorrect, bcrypt.compare() retourne false et le serveur retourne Mot de passe incorrect. Pour les routes protégées, si aucun JWT n'est envoyé, le middleware retourne 401 avec Token manquant. Si le JWT est invalide ou expiré, jwt.verify() déclenche une erreur qui est récupérée par le bloc catch, puis le serveur retourne 401 avec Token invalide. Enfin, les erreurs inattendues provenant du serveur ou de la base de données peuvent être récupérées par les blocs try/catch des contrôleurs et retourner un statut 500. Cette gestion permet au frontend de comprendre le résultat de la requête et d'afficher un message adapté à l'utilisateur.

13. Explication orale pour la présentation

Pour présenter cette partie devant un jury, on peut expliquer que le projet possède un système de sécurité basé sur l'authentification JWT. Lorsqu'un utilisateur crée un compte, le backend reçoit son nom, son email et son mot de passe à travers la route /register. Avant de créer le compte, Sequelize vérifie dans MySQL si l'email existe déjà. Ensuite, le mot de passe est haché avec bcrypt afin qu'il ne soit jamais enregistré en clair dans la base de données. Après la création de l'utilisateur, le serveur génère un token JWT signé avec une clé secrète stockée dans JWT_SECRET. Lors de la connexion, la route /login recherche l'utilisateur avec son email puis utilise bcrypt.compare() pour vérifier le mot de passe. Si les identifiants sont corrects, un JWT est généré et transmis au frontend. Pour protéger une route, par exemple /admin, j'utilise un middleware appelé autorize. Ce middleware récupère le token dans l'en-tête Authorization sous la forme Bearer token et utilise jwt.verify() pour vérifier sa validité. Si aucun token n'est fourni ou si le token est invalide ou expiré, le serveur retourne une erreur 401 et bloque l'accès. Si le token est valide, les informations de l'utilisateur sont placées dans req.user et next() permet à la requête d'accéder à la route protégée. Cette architecture permet donc de séparer clairement l'inscription, la connexion, le hachage des mots de passe, la génération du JWT et la protection des routes. Elle constitue la base de la sécurité backend de mon application.

14. Conclusion

Le système développé permet de mettre en place une authentification complète entre le frontend, le backend et la base de données MySQL. Sequelize assure la communication avec MySQL et permet de définir le modèle User. Les routes Express /register et /login permettent respectivement de créer un compte et de s'authentifier. L'utilisation de bcrypt garantit que les mots de passe ne sont pas stockés directement sous leur forme originale. JWT permet ensuite de représenter l'état d'authentification de l'utilisateur pendant une durée limitée. Le middleware autorize vérifie le token avant de laisser une requête accéder à une route protégée. Grâce à jwt.verify(), le serveur peut vérifier le token et récupérer les informations de l'utilisateur dans req.user. Les routes protégées peuvent ainsi contrôler l'accès aux fonctionnalités sensibles. L'architecture actuelle constitue donc une base solide de sécurité backend avec Node.js, Express, Sequelize, MySQL, bcrypt et JWT. Pour une sécurisation encore plus complète d'une véritable application de production, cette base peut ensuite être renforcée avec une gestion des rôles et permissions, une validation stricte des données, une protection contre les attaques par force brute, HTTPS, une gestion sécurisée du stockage des tokens et une meilleure gestion des informations sensibles.
